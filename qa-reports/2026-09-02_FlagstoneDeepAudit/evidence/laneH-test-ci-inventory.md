## Mock truthfulness + false-confidence patterns

### How Supabase is mocked

**No shared mock factory exists anywhere in the repo** (`src/__tests__/support/` has exactly one file, `stripComments.ts`, unrelated to Supabase; confirmed by directory listing — 60 files do `jest.mock('../supabase', …)` or `jest.mock('@/lib/supabase', …)` and each rolls its own inline mock). Two recurring shapes:

1. **Flexible Proxy chain** (`src/lib/__tests__/flags.supabase.test.ts:57-94`, `makeChain`): every unknown method on the mock chain object returns the proxy itself (so `.select().in().order().limit()` "just works" without enumerating methods), and the chain is `then`-able so `await`ing it resolves via a queued terminal (`mockTerminal`/`mockSingle`/`mockMaybeSingle`). Convenient, but it means the mock **cannot distinguish which chain was actually called** — a test using this pattern proves "the function returned what I told the terminal to return," not "the function built the right query" (contrast with the same file's `updateFlagStatus` CAS test at lines 251-277, which switches to a **recording** mock (`eqCalls: [string, unknown][]`) specifically because the author needed to pin the exact `.eq()` predicates — the file itself documents this gap: *"the conflict tests above can't see WHICH predicate ran — deleting the `.eq('status', expectedCurrent)` line would still pass them"*).
2. **Hand-wired per-table mock** (`src/lib/__tests__/sr050DeleteFlagPhotos.test.ts:57-80`, `wireTables`): `mockFrom.mockImplementation((table) => {...})` branches on the table name and returns a purpose-built chain. More precise (does distinguish `flags` vs `flag_photos` calls) but entirely bespoke per file.

**Default-resolution behavior varies by file, not by any shared convention:**
- `flags.supabase.test.ts` has **no global default** — `mockRpc`/`mockFrom` are bare `jest.fn()`s with no `beforeEach` resolution; a test that forgets to call `setupChain(...)` gets `undefined` back from the terminal, and destructuring `{data, error}` off `undefined` throws a `TypeError` — i.e. the failure mode for "forgot to configure the mock" is a **loud crash**, not a silent false pass.
- `src/lib/__tests__/d1f4r3CanonicalReportDelete.test.ts:13-15` (Build 33) sets an explicit **default-success** resolution in `beforeEach`: `mockInvoke.mockResolvedValue({ data: { status: 'deleted' }, error: null })`. This is a narrower, real false-confidence surface: any *new* test added to that file that forgets to override the mock inherits a silent "delete succeeded" result rather than failing loudly — the three existing tests all do override it, so this is a latent risk pattern rather than a live gap today.
- **Direct answer to the SCOPE question:** `.from().delete().eq().select()` does **not** resolve to success "by default" anywhere — every test that exercises `deleteFlag()` explicitly sets up either a success or an error/empty-array shape per-case (`flags.supabase.test.ts:293-306`, `sr050DeleteFlagPhotos.test.ts:152-313`). `.rpc()` likewise has no default (`requestFlagReopen` tests in `flags.supabase.test.ts:450-491` set `mockRpc.mockResolvedValueOnce(...)` per case). `.functions.invoke()` **does** have a default-success `beforeEach` in the one Build-33 file that uses it, per above.

### RLS / grants / Edge Function deployment — never exercised in Jest, by construction

Every Supabase-touching Jest test mocks `../supabase` (or `@/lib/supabase`) at the module boundary, so **no Jest test in this repo, on either branch, ever executes a real SQL statement, evaluates a real RLS policy, checks a real GRANT, or calls a real (or even locally-emulated) Edge Function.** This is a structural property of running in Node/jsdom, not a gap specific to any one suite — flagged here because it is the reason the Section 29 analysis above concludes client-side "RLS-refusal-shape" tests only prove the **JS interpretation logic** is correct, never that the **actual policy** matches it. The only mechanism in either branch that can prove real RLS/grant behavior is a pgTAP `.sql` file run against a real Postgres — and per the Section 29 evidence, the one such file for flags-delete (`supabase/tests/d1f4r3_fix2_flags_delete_rls.test.sql`, Build-33-only) is never wired into any CI workflow. **No test anywhere hits a real backend** — confirmed structurally (every Supabase-adjacent test file greps positive for `jest.mock(...supabase...)`) and by `jest.setup.js:6-9`, which stubs `EXPO_PUBLIC_SUPABASE_URL` to `http://localhost:54321` (a address nothing is listening on in CI) specifically so `src/lib/supabase.ts`'s `createClient()` can construct without throwing — not so it can connect to anything.

### False-confidence patterns

**1. Source-text "guard" tests — the dominant idiom in this codebase, and self-named as such.** 49 files match `*.guard.test.ts(x)` (e.g. `dismissalStandard.guard.test.ts`, `noCredentialsInTree.guard.test.ts`, `drawerRoutes.guard.test.ts`, `keyboardClass.guard.test.ts`); a broader proxy (`grep -rl readFileSync` across all 243 test files) returns **93 files (38%)** using `fs.readFileSync` to read production source/migrations/config as a string and assert `.toContain()`/`.toMatch()` on it, rather than rendering or executing anything. Self-aware pattern: multiple files' comments name it "the house idiom" and cross-reference each other (`drawerRoutes.guard.test.ts`: *"Static source scans in the house idiom... fast, navigator-mount-free, and they fail the moment the contract breaks"*); `perceptionGuards.test.ts` explicitly hands *runtime* verification to a separate non-Jest tool (`design-reviews/r2-audit/tools/probe-bp2-perception.mjs`, outside this audit's Jest-only scope). **Proves:** the literal string is present/absent, so a text-changing refactor fails loudly — a real tripwire. **Does not prove:** the code *behaves* as the string claims at runtime (a match inside a comment or a dead branch would false-pass), and it is blind to any regression that doesn't touch the exact matched substring. Sharpest example: `d1f4r3Fix2ReviewReplay.test.ts`'s "direct flag deletion containment" tests and `d1f4r3SourceClosure.guard.test.ts` prove the migration **file** contains the right `revoke`/`drop policy` SQL — not that it ever ran against a real catalog.
**2. `noCredentialsInTree.guard.test.ts` — genuinely well-designed but bounded to known shapes.** It re-scans the whole tracked-file census (not just staged diffs, complementing `.husky/pre-commit`'s diff-only scan) for known credential shapes (Supabase JWT/`sb_secret_`, AWS keys, PEM blocks, generic secret-looking assignments), explicitly built in response to a real 62-day credential leak (2026-05-31 incident, documented in the file's own header). Blind spot it shares with the pre-commit hook: it only catches shapes it has a detector for, and (like the hook, per the hook's own S-3 finding) a novel credential format added in the future needs its own new pattern before this test can see it. It also operates on the current working tree only — it cannot say anything about credentials that already exist in Git *history* on commits the repo doesn't currently have checked out.
**3. Dynamic Type tests are honestly scoped, not source-grep.** `src/components/ui/__tests__/AppText.dynamicType.test.tsx` (and its `FlagCard.dynamicType.test.tsx` counterpart) actually `render()` the component and assert the `maxFontSizeMultiplier` prop reaches the underlying `<Text>` — real render, real prop-plumbing assertion, not a text grep. Its own header is explicit about the boundary: *"jest can't measure pixel overflow, so this suite locks the CONTRACT instead"* — it cannot catch a real layout overflow/clipping at 2x+ Dynamic Type, only a silent re-cap of the multiplier constant.
**4. Mock-was-called assertions exist but are typically paired with outcome assertions, not standalone.** Spot-checked across `flags.supabase.test.ts`, `sr050DeleteFlagPhotos.test.ts`, and `admin.test.tsx` — most `expect(mockX).toHaveBeenCalledWith(...)` calls sit alongside an assertion on the resolved/rejected value or rendered output in the same test, rather than standing alone as the only assertion. The `updateFlagStatus` CAS predicate test (`flags.supabase.test.ts:251-277`) is a called-with-only assertion, but it exists specifically because the outcome-only tests next to it (lines 239-246) were shown (by the file's own comment, "F65") to be insufficient — a `mockFrom.mockReturnValue(makeChain(...))` swap without the real `.eq('status', ...)` predicate would still pass them.
**5. Snapshot tests: zero.** `grep -rl toMatchSnapshot` across the whole tree returns nothing. This avoids the classic snapshot-approval false-confidence failure mode (a developer blindly re-approving a snapshot diff) entirely, by never having any.
**6. Screen-level UI tests are the minority; lib-level unit tests dominate.** 105 of 243 files (43%) live under `src/lib/__tests__/`, testing business logic with a mocked backend; only 38 live under `src/screens/__tests__/` and 47 under `src/components/__tests__/` + `src/components/ui/__tests__/` combined. Section 29 and the Journey Coverage matrix below both show the same shape repeating: a well-tested lib function (`deleteFlag`, `deleteAccount`) whose actual UI trigger (`AdminScreen`, `ProfileScreen`, `FlagDetailModal`'s delete button) has no test coverage at all. This is the single most consistent false-confidence pattern in the suite: **passing tests for the function that does the sensitive action say nothing about whether the button that calls it, in the screen a real user taps, is wired correctly, gates on the confirm dialog, or surfaces failures** — see Section 29 and Journey Coverage for the specific instances (`AdminScreen.tsx`, `ProfileScreen.tsx` have zero test files; `FlagDetailModal`'s only test file never touches its delete button).

**WHY_TESTS_WOULD_NOT_CATCH_A_BROKEN_ADMIN_DELETE:**
1. **Mocked-backend class** — every Jest test for `deleteFlag()` (main and Build 33) fully replaces `../supabase`; the mock always returns exactly what the test author scripted. 2. **"Edge Function not deployed" class** — Build 33's `deleteFlag()` depends on a `delete-flag` Edge Function that, per this audit's given production facts, is not deployed. `d1f4r3CanonicalReportDelete.test.ts` mocks `functions.invoke` directly, so it cannot express "the function doesn't exist on this project" as a distinct failure mode from "the function returned an error" — both collapse to the same mocked `{error}` shape. 3. **"Migration not applied" class** — Build 33's entire `flags` DELETE containment story (revoke grants, drop `admin delete any flag`, force everything through the Edge Function) lives in a migration that, per given production facts, is not applied. `d1f4r3Fix2ReviewReplay.test.ts`'s containment assertions and `d1f4r3SourceClosure.guard.test.ts` only read the migration **file** as text — a migration can be 100% textually correct and 100% unapplied, and every one of these guard tests still passes. The one artifact that would catch "unapplied in production" (re-running the pgTAP proof against the actual project) is never automated, per the point above.
4. **No UI-level test on either branch** — even a perfect backend gives no assurance the button wiring is intact: nothing asserts `AdminScreen`'s "Remove flag" press actually calls `deleteFlag` with the correct id, that a thrown error surfaces to the admin instead of silently no-op'ing, or that a stale `flags` array (the optimistic local `filter()`, not a re-fetch) doesn't mask a backend failure that a differently-shaped error object might slip past `catch`.
5. **No CI wiring even for the tests that exist and could catch a real bug** — the sole real-Postgres-backed RLS proof for flags-delete (`d1f4r3_fix2_flags_delete_rls.test.sql`) is scoped to nothing (no workflow references it); the one workflow that *does* boot a real Postgres in CI (`mod1r-fix1-rls-proof.yml`, Build-33-only) is triggered on two specific stale branch names, not `main`, not any branch carrying the flags-delete change, and runs a different SQL pair for a different pair of bugs. ## Coverage gaps

Summary list (each detailed above with file:line evidence):

1. **No UI-level test for any of the three destructive/sensitive actions in the app**: admin flag removal (`AdminScreen.handleRemove`), admin flag dismissal (`AdminScreen.handleDismiss`), owner flag deletion (`FlagDetailModal.handleDelete`), and account deletion (`ProfileScreen`'s delete-account flow). All four are backed by well-tested library functions and zero screen/component tests. See CAND-H-01, CAND-H-02, CAND-H-05, and Section 29.
2. **No automated, CI-wired proof of real Postgres RLS/grant behavior for `flags` DELETE, on either branch.** The one file capable of it (`supabase/tests/d1f4r3_fix2_flags_delete_rls.test.sql`, Build-33-only) is staging-only-by-design and unwired. CURRENT_MAIN has no `supabase/tests/` directory at all. See CAND-H-03.
3. **No end-to-end/device test harness anywhere** (no Playwright, Detox, or Maestro in the repo) — every component-level `it.todo()` stub (32 across 4 files) exists because of this specific gap, and each says so in its own header comment. See CAND-H-06.
4. **`format:check` is not a CI gate** and is documented as unfixable without first making 5 guard tests whitespace-insensitive. See CAND-H-08.
5. **The one workflow that boots a real Postgres in CI (`mod1r-fix1-rls-proof.yml`, Build-33-only) is scoped to two specific stale, non-`main` branch names** and runs SQL files unrelated to the flags-delete RLS question — it provides no ongoing regression protection for `main` or for the branch that actually carries the flags-delete containment work.
6. **The production-submission privacy gate (`eas-testflight-submit.yml`'s `d8_closed` input) is a self-attested string comparison**, not cross-checked against any file or code path. See CAND-H-04.
7. **`react-native-safe-area-context` has no explicit Jest mock wired**, unlike every other native module surveyed (maps, blur, haptics, async-storage all have explicit, deliberate mock treatment). Currently likely dormant risk given thin coverage of inset-consuming screens, but a latent trap for future screen-level tests. See CAND-H-07.
8. **Journey-level coverage is uneven**: sign-in/sign-up testing is narrowly a11y/validation-focused with no "happy path succeeds" or "wrong password" test found by name; leaderboard, settings, and feedback screens each have at most one narrow test file; map filter and search UI (as opposed to their underlying pure filter functions) are not confirmed rendered/interacted with anywhere in this pass. See Journey Coverage matrix.
9. **No test in the repository, on either branch, ever hits a real backend** (structural — every Supabase-adjacent test mocks the client at the module boundary; `jest.setup.js` points `EXPO_PUBLIC_SUPABASE_URL` at an address nothing listens on in CI). This is expected and appropriate for a unit-test suite, but means CI green is never evidence of real integration correctness for anything backend-shaped — a fact this audit's other lanes (backend/RLS/release) should weight accordingly when reconciling "tests pass" against "feature verified in production."
