## DECISIONS FOR SKY

### D1 — Feedback delivery: mailto today, optional Supabase table later

**Status:** APPLIED (mailto). Future option waiting on your call.

This loop shipped feedback as a mailto: handoff to the OS mail composer. Zero schema, zero RLS, zero new dependencies. The user sees what they're sending and edits in their own mail client — no surprise messages on their behalf, easy to upgrade later.

**If you eventually want a tracked feedback table** so messages don't depend on the user actually hitting Send in their mail app, the upgrade is small:

```sql
-- supabase/migrations/<date>_feedback_table.sql (propose-only)
create table public.feedback (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users on delete set null,
  body text not null check (length(body) between 1 and 5000),
  contact_email text,
  platform text,
  created_at timestamptz default now()
);
alter table public.feedback enable row level security;
create policy "anyone can insert" on public.feedback for insert with check (true);
create policy "owner reads only" on public.feedback for select using (
  auth.email() = 'skylerhalisky@gmail.com'
);
```

Then swap `buildMailtoUrl` → an HTTP `supabase.from('feedback').insert(...)` call in `sendFeedback()`, leave the UI unchanged. The two flows can even coexist (insert AND open mail) for redundancy. **Recommendation for now:** keep mailto only — it's user-controlled, no PII at rest, and the volume is unlikely to overwhelm an inbox.

### D4 — Feedback privacy note (Jordan perspective)

**Status:** APPLIED, flagging for your read.

The feedback flow collects free-text from the user and optionally their email. The user sees the message in their own mail composer before sending, so consent is explicit. Nothing is stored on the server today. The platform footer (`Sent from AccessMap on ios`) is included so you can debug platform-specific issues — but it doesn't identify the user.

**If you ever switch to the Supabase feedback table (D1):** the contact_email field becomes PII at rest. You'd want to add: a) a "do not store my email" checkbox on the modal, b) a retention policy (e.g., auto-delete after 90 days), c) an RLS policy that gates SELECT to your owner email only (sketched in D1).

## Per-feature

### F1 — Branded tab headers + global Feedback flow (commit `302cba3`)

**What shipped:** Every tab's header changes from a flat white strip with the tab name to a brand-blue bar with white bold tab name, a subtle drop shadow under the entire header, and a "Feedback" pill in headerRight. Tap → `FeedbackModal` (new component) slides up with a multi-line message field, optional reply email (auto-prefilled from the signed-in user), Cancel and Send buttons. Send hands the URL to `Linking.openURL` (mailto:); the OS opens your mail composer with everything prefilled.

**How to see it:** Open any tab → top of the screen is now brand-blue instead of white → tap the "Feedback" pill at top-right → modal slides up → type a message → tap Send → your mail app opens with To, Subject, and Body filled in.

**Born accessible:** Feedback button has role/label/hint + hit slop 8. Modal: header role on title, every input labeled with hint, send button has busy+disabled accessibilityState, AccessibilityInfo.announce on launch. Brand colors verified against existing AA-checked palette in `theme.ts`.

**Refine vs. remove:** Keep — this is the structural answer to "buttons near the top" and "feedback option."

**Proposed follow-up:** none required. Optional upgrade: D1's Supabase feedback table if you want messages tracked server-side.
