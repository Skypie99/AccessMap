# 04 — Exposure Audit

Per instructions: something is only flagged here if it's a **gap between the intended contract and the implementation**, or a genuine **ambiguity** — not simply because it's intentionally public. Findings are numbered F1–F6 for cross-reference from other files.

## Confirmed-intentional, not a finding

- **`public.flags` full-row anon exposure** (`lat`, `lng`, `description`, `severity`, `category`, `status`, `created_at`, `user_id` UUID, photo fields) — this is the deliberate, twice-reasoned-about (founding Jordan gate + the promptb media-key migration's own privacy note) core of the feature. The raw `user_id` UUID is not independently joinable to PII under `anon` (no anon path to `public.users`). **Already tracked as `FDA-042`** in `supabase/contract/deployed-contract.v1.json` with the note "exposes user_id with precise coordinates" — this is a known, accepted, already-labeled item, not a new discovery. Re-flagging it here would misrepresent existing tracking as new.
- **Anonymous write access** to `flags` (open reports only) and `feedback` (incl. `contact_email`) — directly required by the ratified Privacy Policy's "What you can do without an account" paragraph.
- **Public storage bucket** for flag photos — documented design decision (`docs/SUPABASE_SECURITY.md:26-28`: "acceptable for accessibility flags"), consistent with the Privacy Policy's own photo-caution language ("please keep faces, licence plates... out of frame").
- **`bk_2026_08_22_*` backup tables** — these hold real reporter data (3 user_ids, 66 rows per `qa-reports/.../PROVENANCE.md` cited by the DB agent) but are **confirmed fully revoked** from every role including `service_role` (`phase03a/20260905073925_phase03a_effective_privileges.sql:8-48`) — correctly closed, not a live exposure. (Whether they should be dropped outright vs. retained as revoked residue is a retention-policy question for Phase 05, out of scope here.)

## F1 — `flags.last_moderation_reason_code` is anon-readable; no evidence this was decided

**Severity: needs an owner decision, not urgent.** Added by Phase03B (`phase03b/20260915210256_...sql:19`); only its `UPDATE` is revoked from anon/authenticated/public (`:246`) — `SELECT` is untouched and inherits the blanket table-level anon `GRANT SELECT`. No document found (Phase03A/B packets, DECISIONS_LOG.md, MF05, or code comments) states whether moderation-reason text is meant as public transparency copy or admin-internal reasoning. **Resolve by asking**: is the vocabulary (`flags_last_moderation_reason_code_vocabulary` constraint, `phase03b/20260915210256:24-27`) written to be shown to the flag's reporter/public, or is it moderator shorthand? If the latter, this needs a column-level `REVOKE SELECT` from anon (and probably authenticated-non-admin too).

## F2 — A load-bearing privacy comment in client code is factually false today

**Severity: documentation/trust hazard, not a live leak (the code doesn't gate on it).** `src/lib/flags.ts`, directly above `listFlags()`:
```
* PRIVACY: lat+lng+category is sensitive (location + disability context).
* user_id is included because the Map callout and Tasks card show ownership
* context... RLS on the flags table ensures only authenticated users can
* read rows; PostgREST enforces this before the data reaches the client.
```
This has been **wrong since 2026-05-29** — the moment `"flags readable by anon"` shipped. Whoever wrote/maintained this comment either predates that migration or never reconciled it. It's not currently load-bearing (no code branches on it), but it is exactly the kind of assumption that could cause a future reviewer or implementer to reason incorrectly about the actual RLS posture. Trivial fix, listed in `06_IMPLEMENTATION_PLAN.md`.

## F3 — Two different "is this photo public" answers depending on which table you ask

**Severity: low, but a genuine inconsistency worth a deliberate decision.** The `flags.photo_object_key` (primary photo) is anon-visible end-to-end (anon-readable column → public bucket URL). The `flag_photos` **table** (additional/multi-photo junction, added later) is `authenticated`-only at the RLS layer — but its underlying **storage objects live in the same public `flag-photos` bucket**, so if a guest ever obtained a `flag_photos.object_key`/`url` value by any other means (e.g. a future feature that echoes it, or URL reuse), the bytes would already be fetchable. The table-level `anon` `GRANT SELECT` that already exists on `flag_photos` (Stage-A, `phase03a/20260905073925:223`) with no matching RLS policy is a "dead" privilege today — see F4. Recommend deciding, once, whether additional photos are meant to be as public as the primary one (in which case add the matching anon RLS policy deliberately) or genuinely restricted (in which case the object storage should not be assumed public for those objects either, which is a bigger discussion out of this recon's scope).

## F4 — `flag_photos`/`flag_comments` carry a table-level anon `GRANT SELECT` with no matching RLS policy (defense-in-depth gap, not a live exposure)

**Severity: hardening recommendation, currently harmless.** `phase03a/20260905073925_phase03a_effective_privileges.sql:222-223` grants anon table-level SELECT on both tables. Because RLS defaults to deny with no matching policy, **anon currently gets zero rows from either table** — confirmed by the absence of any `to anon` policy anywhere in the migration history for these two tables. This is safe *today* only because the RLS layer is doing all the work; the grant is a live, unused privilege sitting one `CREATE POLICY ... TO anon USING (true)` away from exposing full comment/photo rows with no further review. Recommend narrowing the grant to `authenticated` only (matching intent) as defense-in-depth — not urgent, but cheap and removes a latent risk class.

## F5 — Account-deletion machinery referenced by 5 of 7 edge functions does not exist in `supabase/migrations/`

**Severity: directly touches the "deletion/takedown state" threat-audit item — needs live verification before Phase 03C implementation, not a read-privacy issue per se.** `supabase/functions/{delete-account,account-deletion-worker,account-deletion-review,account-deletion-status,delete-flag}/index.ts` collectively call 11 RPC names (`request_account_deletion`, `claim_next_account_deletion_operation`, `account_deletion_requires_review`, etc. — full list in the DB agent's §4) that **do not appear anywhere in `supabase/migrations/`**. They exist only as drafts under `supabase/nonmanaged/proposed/`. Given `01_GROUND_TRUTH.md`'s finding that `migrations-next/` content the DB agent dismissed as "unapplied" turned out to be live, **this session cannot rule out that these RPCs are also live via some other out-of-band or not-yet-reviewed path** — but no equivalent ledger-arithmetic evidence was found confirming them (unlike Stage-A/03B, no R02-style inspection or closure report mentions an account-deletion migration batch). Best current read: **genuinely not applied** — the account-deletion feature is functions-layer code calling into database functions that don't exist, which would fail at runtime, not silently over-expose data. Flagged as AMBIGUITY A1 in `07_OPUS_HANDOFF.md` — resolve with a live, read-only `to_regprocedure()` check before relying on either conclusion. This directly affects the read-contract because the Privacy Policy promises "Deleting your account permanently removes... reports and their associated content... uploaded photos" — if the mechanism doesn't exist, deleted-account data may still be anon-readable via the ordinary `flags`/`flag_photos` public paths, which would be a real contract violation, not just an internal bug.

## F6 — Legacy `flags_user_scoped` policy: textually still present, worth a live check

**Severity: low, likely inert, quick to confirm.** `flags_user_scoped` (`ALL`, `user_id = auth.uid()`, created `20260528180513_d1_flags_rls.sql:13-16`) is never explicitly `DROP POLICY`'d by name in `supabase/migrations/` (per the DB agent's §2 note) — though it's superseded in practice by the narrower per-command policies added afterward. The deployed-contract capture (`supabase/contract/deployed-contract.v1.json`, dated 2026-09-05, cited by the client-surface agent) independently flagged this as `FDA-009`: `roles: ["PUBLIC"]`, "legacy overlapping ALL policy still present." Multiple restrictive/permissive PERMISSIVE policies combine with OR logic in Postgres RLS, so an inert-looking leftover permissive policy scoped to `PUBLIC` (which includes `anon`) is worth a direct `pg_policies` check, not an assumption either way — especially since this finding predates (2026-09-05) the Stage-A/03B changes this recon relies on, and could have been cleaned up, tightened, or could still be sitting there unnoticed.

## Non-findings explicitly ruled out

- **SECURITY DEFINER privilege escalation**: every SECURITY DEFINER function reviewed either has no meaningful side effect reachable by a lower-privileged caller (trigger-only, fires on the owner's own action) or has an explicit `current_user_is_admin()`/`auth.uid()` check gating the sensitive branch. `notify_flag_status_webhook()`'s hardcoded secret + missing `search_path` is a **pre-existing, already-documented finding** (`20260602060359_flags_close_nonowner_delete_and_fix_triage.sql:65-68`, "Rotate both + move to Vault/config" — still open per the DB agent, but not new to this recon and not an anon-read issue).
- **Column leakage via client-side `.select()` lists**: confirmed as a real *pattern* worth naming (client-surface agent §4 — every explicit column allowlist in `src/lib/*.ts` is a convention, not a boundary) but **not currently exploitable beyond what RLS already permits row-wide** for `flags` (anon already has the whole row) or blocked entirely for `flag_comments`/`flag_photos`/`users` (RLS denies regardless of what a raw REST call requests). No column exists today that's in a table's schema but excluded from both the client select *and* from RLS/grant exposure in a way that would matter — i.e., there's no column currently "hidden" only by client convention while a raw call could get it, other than what F1 already covers.
- **Moderation/admin field leakage to anon**: `is_admin` is **not** anon-readable at any point in the history (confirmed independently by this session, the DB agent, and the client-surface agent). It **is** readable by any *authenticated* (non-admin) user table-wide, as a **documented, owner-accepted Stage-A compatibility retention** pending the excluded Stage B (`phase03a/20260905073925_...sql:249-252`, comment: "This line is the WHOLE of the is_admin compatibility retention. Stage B revokes it"). This is outside the anon/public-read contract's scope (the task's own title) but is directly the threat-audit's "moderation/admin/internal fields" category applied to `authenticated` rather than `anon` — recorded here for completeness, not as a Phase 03C action item, since it already has an owner-approved deferral.
