## 3. Auth Boundaries ✅ SOLID

RLS is enabled on every table. Policy review:

| Table | Read | Insert | Update | Delete |
|---|---|---|---|---|
| `public.users` | authenticated only | trigger only | own row only | cascade from auth |
| `public.flags` | authenticated only | own `user_id` | own row OR status-only patch | own row only |
| `public.push_tokens` | own row only | own `user_id` | own row only | own row only |
| `storage.objects` (flag-photos) | public URL (no LIST) | own folder path | — | own folder path |

The triage `WITH CHECK` on `flags` (the "status-only update by any authenticated" policy) correctly pins all non-status columns to their existing values via correlated subselects. A non-owner cannot sneak in a `user_id`, `lat`, `lng`, `category`, `severity`, `description`, or `photo_url` change through the triage path. **This is the most important RLS clause in the app and it is correct.**

Security-definer functions (`handle_new_user`, `handle_flag_status_change`) both have `REVOKE EXECUTE FROM public, anon, authenticated` — not callable via the REST API. ✅

Client-side: all Supabase calls rely on RLS for enforcement (no client-side ownership check before queries), which is the correct pattern. ✅

## 5. Error Handling ⚠️ MINOR GAP

`errorMessage(e)` returns `e.message` verbatim. Supabase/PostgREST errors can include strings like:
- `"null value in column 'severity' violates not-null constraint"` — reveals column names
- `"violates foreign key constraint 'flags_user_id_fkey'"` — reveals FK name
- `"column 'context_tags' does not exist"` — reveals migration state

These are shown in `Alert.alert()` dialogs. Not exploitable (RLS prevents unauthorized access), but leaks DB schema internals to the user. Low severity. See Proposal P2-b.

Auth errors from Supabase (`signIn`, `signUp`) surface `error.message` directly — this is correct; those messages are explicitly user-facing ("Invalid login credentials"). ✅

Sentry init correctly skips when no DSN is configured. ✅

These were reintroduced by the TestFlight wiring commit `1be62d4`, which overwrote Jordan's privacy gate commit `4239748`.

## Proposals (DECISIONS FOR SKY)

### P1 — Validate deep-link `flagId` as UUID before DB query

**Current behavior:** `accessmap://flag/not-a-uuid` → `fetchFlagById("not-a-uuid")` → PostgREST returns a type error (invalid UUID input syntax) → MapScreen swallows it. No auth bypass, no data leak, but a wasted round-trip and server-log noise.

**Exact fix** (3 lines in `MapScreen.tsx`, inside the `useEffect` that reads `route.params?.flagId`):
```ts
// UUID v4 format check before hitting the DB — malformed deep links open map normally
const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i;
if (!flagId || !UUID_RE.test(flagId)) return;
```
Add this immediately before the `fetchFlagById(flagId)` call.

### P2-b — Sanitize PostgREST error messages shown in Alert dialogs

**Current:** `errorMessage(e)` returns raw `e.message`. Constraint-violation messages leak column and FK names to the user.

**Exact approach** (`src/lib/errors.ts`): add a sanitize pass for known PostgREST patterns before returning. Auth error messages (from `supabase.auth.*`) should be excluded from sanitization — they're intentionally user-facing.

```ts
const DB_ERROR_PATTERNS = [
  'null value in column',
  'violates foreign key constraint',
  'violates check constraint',
  'column ',
  'relation ',
];

function sanitizeDbMessage(m: string): string {
  if (DB_ERROR_PATTERNS.some(p => m.toLowerCase().includes(p.toLowerCase()))) {
    return 'Something went wrong. Please try again.';
  }
  return m;
}
```

Wire it into `errorMessage()` so callers get it automatically. Auth-flow `error.message` values come from Supabase Auth (not PostgREST) so they won't match these patterns and will pass through unchanged.

### P3 — Configure Sentry DSN before the App Store build

**Issue:** `EXPO_PUBLIC_SENTRY_DSN` is absent from `.env`. `initSentry()` silently skips when the DSN is empty. Production crashes are invisible.

**Steps:**
1. Log in to sentry.io → Projects → AccessMap → Settings → Client Keys → copy the DSN.
2. Add to EAS secrets: `eas secret:create --scope project --name EXPO_PUBLIC_SENTRY_DSN --value <dsn>`
3. Rebuild via EAS and confirm events appear in Sentry after the first TestFlight session.

No code change needed — `sentry.ts` already reads `process.env.EXPO_PUBLIC_SENTRY_DSN`.
