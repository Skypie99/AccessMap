## Identity and admission options

| Architecture | Same-network clients | Reset/bypass and privacy consequence | Assessment |
|---|---|---|---|
| Short-window server HMAC of a verified source IP | A and B sharing one public IP still share one bucket. | HMAC changes representation, not cardinality; changing networks can change the bucket. Short retention can improve privacy. | Potential network/emergency control only; fails independent same-NAT normal budgets. |
| Server-issued, short-lived random capability | Distinct issued sessions can have distinct budgets, even on the same network. | A can discard its token and request another unless issuance is independently controlled. Signature verification prevents fabrication, not repeated legitimate minting. Binding issuance only to IP restores shared-network contention. | Feasible **per-session** mechanism; insufficient proof of reset-resistant per-client budgets without an explicit admission/identity decision. |
| Client-generated key or proof-of-possession token | Keys can be separate. | An anonymous caller can generate another key. Proof of key possession does not establish one entitlement per client. | Same unresolved issuance problem. |
| Supabase anonymous Auth | Distinct created users receive distinct IDs. | Creates Auth records and sessions; fresh signup produces another identity. Anonymous users use `authenticated`, requiring policy review. | Material identity, retention and authorization change; not an automatic fit for the owner's privacy contract. |
| CAPTCHA/Turnstile admission plus short capability | Can admit separate sessions behind one IP. | A challenge can constrain minting cost; a successful token is not documented as a unique-device entitlement. Requires provider/UI integration and an explicit abuse model. | Owner decision; cannot claim strict client uniqueness from challenge success. |
| Turnstile Ephemeral IDs | Vendor offers device-linked signals independent of IP. | Official docs describe account-scoped identifiers lasting up to a few days, Enterprise entitlement, and account-team enablement. | Material provider/access and device-linking privacy tradeoff, not existing Supabase metadata. No entitlement or suitability verified. |

The first three rows are architectural inferences. The owner has not precisely defined whether a “client” is one short-lived session or must retain its exhausted budget after clearing session state. Under the latter interpretation, if a returning caller can present exactly the observations of a fresh same-network client, a server cannot reliably classify one as A and the other as B without an additional trusted distinction. This is the specific missing identity/admission primitive, not a claim that all anonymous abuse prevention is impossible.

A session credential should not contain the internal bucket key. Even with a separate internal derivation, sending a credential that selects a budget needs explicit reconciliation with the owner's “no internal rate-limit identifiers to the client” rule; terminology alone does not settle that privacy boundary.

[Anonymous Auth documentation](https://supabase.com/docs/guides/auth/auth-anonymous) says anonymous users are stored, use the authenticated database role with an `is_anonymous` claim, and lack automatic cleanup. [Session documentation](https://supabase.com/docs/guides/auth/sessions) describes indefinite default session duration and refresh tokens. [Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits) impose an IP-based anonymous-signup budget; that does not provide independent same-NAT admission. Current docs disagree on configurability, so this review makes no project-setting claim.

For this codebase, adoption would require reviewing the Auth-to-profile mirror and authorization: at receipt HEAD `c794ba8544df2f128269eabf6d87c9ed07a8fd68`, `supabase/schema.generated.sql:586–595` copies Auth ID/email into `public.users`, whose email is non-null at `1078–1080`; `supabase/migrations-next/20260904000200_adopt_d1sa_containment.sql:79–96` grants status-update policy eligibility by profile existence; `supabase/migrations-next/phase03a/20260905055630_phase03a_open_inserts.sql:6–7` restricts authenticated INSERT status, without distinguishing anonymous Auth. This is a compatibility dependency, not a proven signup failure. The review did not adopt anonymous Auth or assess the parent's subsequent uncommitted FDA-012 edits as an accepted candidate.

[Turnstile validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/) requires server verification; tokens expire after five minutes and are single-use, with `remoteip` optional. Those guarantees prevent replay of one proof, not obtaining fresh proofs. [Ephemeral IDs](https://developers.cloudflare.com/turnstile/additional-configuration/ephemeral-id/) are a distinct Enterprise feature. Neither was provisioned or accepted here.

## What useful implementation can and cannot solve

A shared atomic counter and service-only ingestion can use the existing private Postgres boundary; a new Redis service is not inherently necessary. Process-local counters cannot enforce one global budget across concurrent Edge isolates. Supabase's [limiter example](https://supabase.com/docs/guides/functions/examples/rate-limiting) demonstrates shared counters and an authenticated-user model, not proof of anonymous identity. The platform's documented [recursive-call limiter](https://supabase.com/docs/guides/functions/recursive-functions) applies to internal function-to-function traffic, not the inbound guest budget.

After identity/admission is resolved, the complete design must close direct guest flag and feedback INSERT, exposed RPC alternatives, and any authenticated/null-user route that still functions as guest ingestion. Every accepted guest path must reach the same trusted budget decision; a caller-selected ID or fallback global bucket cannot bypass it. Keep the existing global database cap as emergency protection. The parent owns the detailed caller/privilege audit and implementation; no direct guest capability is revoked by this review.

Minimum evidence must include same-network synthetic A/B isolation, quota exhaustion, concurrent requests, token renewal/reset/pre-mint behavior, forged and duplicate candidate headers, missing metadata, all alternate ingest paths, emergency-cap behavior, expiry/cleanup and restoration. Receipts should contain only outcomes, counts, bounded lifetimes and source/version provenance. Do not emit raw network values, internal bucket keys, tokens or secret-derived identifiers. Application-data privacy proof must not be generalized into a claim that platform infrastructure has no request logs.
