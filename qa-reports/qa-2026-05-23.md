## Headline finding (HIGH)

**RLS policy contradicts the points trigger and the Tasks UI.**

| File | Lines | What it says |
| --- | --- | --- |
| [`supabase/schema.sql`](../../../AccessMap/supabase/schema.sql) | 157–162 | `"flags update own"` — UPDATE only allowed when `auth.uid() = user_id` |
| [`supabase/schema.sql`](../../../AccessMap/supabase/schema.sql) | 103–108 | Points trigger awards **actor bonus** when `auth.uid() <> new.user_id` — i.e. when a non-owner triages |
| [`src/screens/TasksScreen.tsx`](../../../AccessMap/src/screens/TasksScreen.tsx) | 86–111 | Client lets *any* authenticated user tap Verify / Resolve / Reject on *any* flag |

The trigger and UI assume non-owners can change `status`. The RLS
forbids it. The actor-bonus branch in the trigger can never fire
under the current policy. In production with multiple users, all
non-owner triage attempts will silently fail with a Postgres RLS
error — the user sees nothing, the points don't move, the flag
status doesn't change.

This is the kind of thing that fails *invisibly* in solo testing
and *exactly* when you ship.

**Confirmed design intent (you, 2026-05-23):** any authenticated
user should be able to triage any flag.

**Fix is propose-only** because it touches RLS. Exact steps in the
propose-only section below (P-NEW-1).

### 1. `fix: handle getSession() rejection so loading always resolves` — `69078ec`

- **Severity:** medium (latent infinite-loading bug)
- **File:** [`src/lib/auth.tsx`](../../../AccessMap/src/lib/auth.tsx)
- **What was wrong:** `supabase.auth.getSession().then(({ data }) => …)`
  had no `.catch()`. If the call rejected (offline at launch, Supabase
  unreachable, JWT decode error), the error was silently swallowed
  and `loading` never flipped to `false`. The AuthProvider sat on a
  blank screen forever.
- **What changed:** Wrapped the call in a `try/catch/finally` async
  IIFE. `loading` always becomes `false`; session stays `null` on
  failure; the auth gate falls through to `SignInScreen`. The error
  is logged with a `console.warn` prefix `[auth]` for debugging.
- **Why safe:** Strict superset of previous behavior. Happy path
  identical. Failure path becomes "show sign-in" instead of "stuck
  loading" — i.e. fails *safely*.
- **How to smoke test:** Force-quit the app with airplane mode on,
  relaunch. Previously the loading spinner spun forever; now it
  resolves to SignInScreen within a second.

## Propose-only (NOT applied — needs your hands)

### P-NEW-1 — Allow non-owner triage of flags (the HIGH finding)

**Why it matters:** see the Headline Finding above. Without this,
the moderation flow is broken in any multi-user scenario.

**Approach (confirmed by you):** add a second UPDATE policy that
lets any authenticated user update *only* the `status` column. The
existing `"flags update own"` policy stays, so owners keep full
edit rights on their own description / photo / severity.

**Exact steps (Supabase Dashboard → SQL Editor):**

1. Open [`supabase/schema.sql`](../../../AccessMap/supabase/schema.sql)
   and add this block right after the existing `flags update own`
   policy (around line 162):

   ```sql
   drop policy if exists "flags status update by any authenticated" on public.flags;
   create policy "flags status update by any authenticated"
     on public.flags for update
     to authenticated
     using (true)
     with check (
       -- Only the status column can change via this policy.
       -- All other columns must equal their previous values.
       user_id    = (select user_id    from public.flags where id = flags.id)
       and lat         = (select lat         from public.flags where id = flags.id)
       and lng         = (select lng         from public.flags where id = flags.id)
       and category    = (select category    from public.flags where id = flags.id)
       and severity    = (select severity    from public.flags where id = flags.id)
       and description is not distinct from (select description from public.flags where id = flags.id)
       and photo_url   is not distinct from (select photo_url   from public.flags where id = flags.id)
       and created_at  = (select created_at  from public.flags where id = flags.id)
     );
   ```

2. Run the updated `schema.sql` via the SQL Editor (it's idempotent —
   the `drop policy if exists` line makes re-runs safe).

3. In the Dashboard → **Authentication → Policies**, confirm BOTH
   policies are listed on `public.flags`:
   - `flags update own`
   - `flags status update by any authenticated`

4. Smoke test (needs two accounts):
   - Account **A** creates a flag.
   - Account **B** opens **Tasks**, taps **Verify** on A's flag.
     - ✅ Expected: status flips to `verified`, B's points go up by
       **+2**, the trigger fires the actor-bonus path.
   - Account **B** tries (via direct SQL or REST) to change A's
     flag's description.
     - ✅ Expected: **rejected** — the new policy only allows status
       changes, and the owner policy requires `auth.uid() = user_id`.

**Risk / blast radius:** Medium. Adding policies is reversible
(`drop policy "flags status update by any authenticated";` undoes
it). The risk is mostly in the WITH CHECK expression — re-read it
carefully and run the two smoke tests above before declaring it
done.

### P-NEW-2 — Persistent flag-load error indicator on the Map

**Why it matters:** [`MapScreen.tsx:120-137`](../../../AccessMap/src/screens/MapScreen.tsx)
shows a one-shot `Alert` when the initial flag fetch fails, then
renders an empty map. The user can't tell **"0 flags here"** from
**"fetch failed"**. On a flaky network this is silently misleading —
someone might assume an area is accessibility-clear when really the
data didn't load.

**Exact steps:**

1. Add a `loadError: string | null` state alongside `loadingFlags`.
2. In the `refreshFlags` catch block, set `loadError` to a short
   message (e.g. `'Couldn't load flags. Tap to retry.'`).
3. Render a small persistent banner above the map (or repaint the
   refresh button into an error variant) whenever `loadError` is set.
4. Clear it on successful refresh.
5. Keep the existing `Alert` *or* drop it — banner alone is fine.

**Risk / blast radius:** Low. UI-only addition. No data flow change.

### P-NEW-3 — `updateFlagStatus` should return the awarded points

**Why it matters:** This is the deeper version of the issue the
prior pass's commit `25ce0d5` patched. The Tasks-screen flash banner
hardcodes `+5 / +10 / +2 / +5` matching the trigger constants in
[`supabase/schema.sql`](../../../AccessMap/supabase/schema.sql). If
the trigger numbers ever change, the UI silently lies. The previous
report acknowledges this at the bottom but doesn't propose a fix.

**Exact steps:**

1. Replace the existing trigger with a `SECURITY DEFINER` RPC
   `set_flag_status(flag_id uuid, new_status flag_status)` that
   does the auth check + status update + points update, and
   returns `{ reporter_bonus int, actor_bonus int }`.
2. Update
   [`src/lib/flags.ts`](../../../AccessMap/src/lib/flags.ts)
   `updateFlagStatus(flagId, status)` to call the RPC and return
   the payload.
3. Update
   [`src/screens/TasksScreen.tsx`](../../../AccessMap/src/screens/TasksScreen.tsx)
   `setStatus` to read the returned points instead of computing
   them client-side.
4. Delete the hardcoded `+5 / +10 / +2 / +5` strings and the
   `isOwn` branch.

**Risk / blast radius:** Medium-high. Touches schema, an RPC, and
two client files. Save for a dedicated session — this is not a
one-line fix.

**Side benefit:** This refactor also obviates P-NEW-1 partially —
if the RPC owns the auth check, the RLS policy on UPDATE can stay
restrictive and the RPC bypasses it via `SECURITY DEFINER`. Either
P-NEW-1 *or* P-NEW-3 will fix the moderation flow; P-NEW-3 is the
better long-term fix; P-NEW-1 is the faster band-aid.

## Forward-looking suggestions

1. **Add a single two-account integration test before any more
   game-mechanic work.** The HIGH RLS finding above would have been
   caught immediately by even the dumbest "Account B verifies
   Account A's flag" test. You don't need a full test framework —
   a single Node script that signs in as two test users via the
   Supabase JS SDK and exercises `updateFlagStatus` is ~50 lines
   and would have caught this. Pair this with P8 (CI workflow)
   from the prior pass and you get a permanent regression-net.

2. **Couple UI strings to server truth.** P-NEW-3 is the canonical
   example: whenever the UI hardcodes a number that *also* lives
   in the database (point values, status labels, severity colors),
   there's a hidden sync hazard. The longer this drifts, the harder
   it is to undo. Worth doing once before more game-mechanic tweaks
   land. The pattern generalizes — make the server tell the client
   what just happened, don't make the client guess.

3. **(Continuous-improvement system meta-suggestion.)** This pass
   re-discovered the RLS gap because the audit looked at the
   *interaction* between the policy, the trigger, and the UI as a
   single system — not as three isolated artifacts. Worth bumping
   the safety-and-robustness skill's checklist to include a
   "Walk the data flow end-to-end" pass: pick the top user action,
   trace it from the button click through the client call, the
   policy check, the trigger, and the response payload. Bugs that
   live in the seams between layers are systematically harder to
   find via single-file scans. I'd add this to the SKILL.md
   instructions on the next iteration.
