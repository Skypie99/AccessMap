### D3 — Privacy: server-side feedback collects free text + optional email

**Status:** APPLIED in the SQL schema, flagging for your read.

The new `public.feedback` table captures: `body` (free text, ≤5000 chars), optional `contact_email` (validated against a basic regex), `platform` (`ios`/`android`/`web`), and `user_id` (nullable — anonymous inserts allowed by the RLS policy `feedback_insert_self_or_anon`).

**Privacy properties:**
- A user can only SELECT their own rows (`feedback_select_own`) — they cannot read others' feedback.
- The maintainer email (`skylerhalisky@gmail.com`) can SELECT everything (`feedback_select_maintainer`) for triage.
- A user can DELETE their own rows (`feedback_delete_own`) — right-to-be-forgotten.
- No UPDATE policy on purpose — feedback is intentionally append-only from clients.

**If you want to harden further** (after applying the migration):
- Add a retention policy (e.g., auto-delete `feedback` rows older than 180 days) via a scheduled Supabase function.
- Make `contact_email` opt-in via a checkbox in `FeedbackModal` (currently auto-prefilled from the signed-in user).
- Add a "redact PII before send" pass on the client.

**For the current scope:** the table is private by default and the user is in control of what they send.

**Refine vs. remove:** Keep.

### F2 — Supabase feedback table + dual-write (commit `a746ad5`)

**What shipped:**
- New propose-only migration: `supabase/migrations/2026-05-23_feedback_table.sql` (134 lines, idempotent, includes HOW TO APPLY + rollback inline).
- New library: `src/lib/feedbackStore.ts` with `submitFeedback()` and `listFeedbackByUser()`. Both wrap supabase calls in try/catch and return discriminated unions (`'inserted'`/`'skipped'` and `FeedbackRow[]`).
- New types in `src/types/database.ts`: `FeedbackRow`, `FeedbackCategoryRow`, and a `feedback` block in `Database['public']['Tables']`. Uses `type` per the load-bearing CLAUDE.md rule.
- `FeedbackModal` dual-writes: fires the insert in parallel with the mailto, doesn't await its result for UI gating. Logs `skipped` reasons to `console.warn` for dev visibility.

**How to see it (after applying the migration):** Send feedback → mailto opens AND a row appears in the dashboard's `feedback` table. Before applying, only the mailto fires.

**Born safe:** The dual-write pattern means the user NEVER sees a server-side error. Until the migration runs, every insert returns `{status:'skipped'}`. After it runs, server tracking lights up with zero client change.

**Refine vs. remove:** Keep. This is the architectural answer to "messages don't depend on the user actually hitting Send in their mail app." See D1 to apply the migration.

**Proposed follow-up:** if you want a "thanks!" confirmation that's authoritative (i.e., only shown when the server insert succeeded), the modal could await the insert result before closing. Today it returns immediately so the user isn't blocked by a slow network — tradeoff is the "thanks" doesn't promise the message reached the server. Easy to flip later.

### F3 — My Feedback history page (commit `e73f4e2`)

**What shipped:** New `MyFeedbackModal` component, opened from a new "My Feedback" row in Profile (between My Reports and About). Lists the user's past feedback rows from `listFeedbackByUser()`, newest first. Each row card shows the category pill (with glyph + label), date, and a 200-char body preview. Pull-to-refresh wired via RefreshControl.

Empty-state card with a 💬 icon, "No feedback yet" headline, and a hint pointing to the header's Feedback button. Same card displays whether the user just hasn't sent anything OR the migration isn't applied yet — UX-equivalent.

**How to see it:** Profile tab → "My Feedback" row → modal slides up. With migration applied + feedback sent, your rows appear. Without either, the empty-state card explains what to do.

**Born accessible:** Each row card has an `accessibilityLabel` that combines category + date + body preview so AT reads a complete sentence per row. Decorative glyphs hidden from AT.

**Refine vs. remove:** Keep.

### F4 — Help & FAQ page (commit `b903e26`)

**What shipped:** New `HelpModal` component, opened from a new "Help & FAQ" row in Profile (sibling to About). 7 seed questions in a `FAQS` constant covering: how to report, how points work, verified vs resolved, photo/location privacy, screen-reader behavior, deleting a report, filter-hiding. Each item is independently expand/collapsible (only one open at a time). Footer brand-soft card with an "Email us" button that hands straight to the mail composer.

Adding more Q&A later is a one-line append to `FAQS`.

**Born accessible:** Each FAQ question Pressable has `accessibilityRole="button"` + `accessibilityState.expanded` + a hint that spells what tapping does. Chevron glyphs are `accessibilityElementsHidden` — the expanded state on the button carries the meaning.

**Refine vs. remove:** Keep.
