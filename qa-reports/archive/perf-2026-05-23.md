## Optimizations made (branch `perf/auto-2026-05-23`)

### 1. Cache web map `divIcon` by color + dim · High · `src/components/PlatformMap.web.tsx`
- **The cost:** Every parent re-render rebuilt a fresh `L.divIcon` for **every marker**.
  Leaflet treats a new icon object as a marker change, which forces it to re-render.
  At 500 capped flags that's 500 wasted allocations + 500 unnecessary marker updates
  per render.
- **The fix:** Tiny `Map<string, L.DivIcon>` keyed by `${color}|${dim}`. There are only
  ~12 possible combinations (6 severity colors × 2 dim states) so the cache is bounded.
- **Expected impact:** DivIcon allocations per render go from O(N) to O(1). On the web
  build, pan/zoom over a dense screen should feel meaningfully smoother once flag
  counts grow.
- **Commit:** `16307e5`

### 2. Prune stale marker refs · Med · `src/components/PlatformMap.tsx`, `…web.tsx`
- **The cost:** `markerRefs.current` is keyed by flag id. React calls the ref callback
  with `null` on unmount, but the key stays. After a long triaging session, dead
  entries accumulate one-per-resolved-flag.
- **The fix:** `useEffect([flags])` that prunes keys not present in the current flag
  list.
- **Expected impact:** Small constant memory win that scales with throughput of
  resolved/rejected flags; bigger value is removing a quiet leak before it shows up.
- **Commit:** `bfbcd6d`

### 3. Memoized `FlagCard` in `TasksScreen` · High · `src/screens/TasksScreen.tsx`
- **The cost:** `renderItem` was an inline function that closed over `busyId` and
  `user?.id`. Flipping `busyId` for the single card you tapped re-rendered **every
  visible card**, because each card's `renderItem` closure was new.
- **The fix:** Extract `FlagCard` as a `React.memo`'d component with explicit props
  (`flag`, `isBusy`, `isOwn`, `onPress`, `onSetStatus`). Wrap parent callbacks in
  `useCallback` so they're stable across renders. Only the row whose `isBusy` actually
  changes re-renders.
- **Expected impact:** Per-action card renders go from O(visible rows) → 1. At ~50
  rows on screen this is the difference between snappy and laggy taps.
- **Commit:** `6022cf7`

## Proposals (NOT applied — need your review)

These are the higher-leverage wins, but each touches schema, dependencies, or a
dashboard toggle. They're listed in roughly priority order.

### Proposal A — bounding-box flag loading (lightweight, no PostGIS)
**Why it matters at scale:** `listFlags` currently pulls up to 500 rows ordered by
recency, regardless of where the user is on the map. At 10k flags you start dropping
real reports from view; at 100k the response payload alone is a problem.

**Lightweight approach (no PostGIS, no new extension):**
1. Add a region-based fetch:

   ```ts
   // src/lib/flags.ts
   export interface Bbox {
     minLat: number; maxLat: number;
     minLng: number; maxLng: number;
   }
   export async function listFlagsInBbox(
     statuses: FlagStatus[] = ['open', 'verified'],
     bbox: Bbox,
   ) {
     const { data, error } = await supabase
       .from('flags')
       .select('id,user_id,lat,lng,category,description,severity,photo_url,status,created_at')
       .in('status', statuses)
       .gte('lat', bbox.minLat).lte('lat', bbox.maxLat)
       .gte('lng', bbox.minLng).lte('lng', bbox.maxLng)
       .order('created_at', { ascending: false })
       .limit(500);
     if (error) throw error;
     return (data ?? []) as FlagRow[];
   }
   ```
2. Have `PlatformMap` expose `onRegionChange` and call this debounced (~400ms) when
   the user pans or zooms.
3. Optionally drop the existing `flags_geo_idx` (btree on `(lat,lng)` is the wrong
   shape for bbox) and add a composite `(lat,lng)` index — Postgres can use a
   well-ordered composite for range scans on lat, with lng as the secondary key.

**Expected impact:** rows fetched per map open: entire table → only what's on screen.
At 10k flags that's a ~95% drop in payload for a city-block-zoomed view.

**Risk:** behavior change — the Tasks list also uses `listFlags` and *does* want
recency, not viewport. Keep the old `listFlags(...)` for Tasks; add the new one for
Map.

---

### Proposal B — PostGIS migration (scalable path, deeper change)
The real industry pattern for "load what's on screen" is PostGIS. Heavier lift but
the cleanest answer past tens of thousands of flags.

1. **Supabase dashboard → Database → Extensions:** enable `postgis`.
2. **SQL:**
   ```sql
   alter table public.flags add column geom geography(point, 4326)
     generated always as (st_setsrid(st_makepoint(lng, lat), 4326)::geography) stored;
   create index if not exists flags_geom_gist on public.flags using gist (geom);

   create or replace function public.flags_in_view(
     min_lat double precision, min_lng double precision,
     max_lat double precision, max_lng double precision,
     statuses text[] default array['open','verified']
   ) returns setof public.flags
   language sql stable security invoker as $$
     select * from public.flags
     where status = any(statuses)
       and geom && st_makeenvelope(min_lng, min_lat, max_lng, max_lat, 4326)::geography
     order by created_at desc
     limit 500;
   $$;
   ```
3. Call from the client:
   ```ts
   const { data, error } = await supabase.rpc('flags_in_view', {
     min_lat, min_lng, max_lat, max_lng, statuses: ['open','verified'],
   });
   ```
4. Drop the old `flags_geo_idx` (`btree(lat,lng)`) — superseded by the GIST index.

**Expected impact:** spatial queries that today scan the table use a real geo index.
Combined with debounced region-change fetching, peak rows per map open stays bounded
no matter how big the table gets.

**Risk:** schema migration; you'd want to backfill the generated column once and verify
in a non-prod branch first. Test on a Supabase database branch before promoting.

### Proposal C — RLS `(select auth.uid())` initPlan rewrite
**Why it matters at scale:** Today every authenticated row read evaluates
`auth.uid()` once per row. Supabase's docs explicitly recommend wrapping as
`(select auth.uid())` so the planner runs it once as an initPlan. Documented
speedup is often **>100x** on large tables. Costs you nothing functionally; it's
purely a planner hint.

**SQL (drop-in replacement for `supabase/schema.sql`):**
```sql
drop policy if exists "users update own row" on public.users;
create policy "users update own row"
  on public.users for update
  to authenticated
  using ((select auth.uid()) = id)
  with check ((select auth.uid()) = id);

drop policy if exists "flags insert own" on public.flags;
create policy "flags insert own"
  on public.flags for insert
  to authenticated
  with check ((select auth.uid()) = user_id);

drop policy if exists "flags update own" on public.flags;
create policy "flags update own"
  on public.flags for update
  to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);

drop policy if exists "flags delete own" on public.flags;
create policy "flags delete own"
  on public.flags for delete
  to authenticated
  using ((select auth.uid()) = user_id);
```
Already keyed `to authenticated` (good — anon short-circuits). `flags_user_id_idx`
already exists.

**Expected impact:** writes against `flags`/`users` get a major speedup as those
tables grow. Free win.

**Risk:** none functional — same authorization, same result. Pure planner hint.
Still propose-only because it's a schema-file change and should be applied via the
Supabase SQL editor.

### Proposal D — marker clustering
**Why it matters at scale:** every flag renders as its own marker on both platforms.
Hundreds of pins will jank pan/zoom; thousands break it. Clustering groups nearby
pins until you zoom in.

- **Native:** `react-native-clusterer` (C++/JSI; best fit for the New Architecture).
- **Web:** `leaflet.markercluster` or a `supercluster` integration.
- Both wired **inside `PlatformMap` only** — never from a screen (CLAUDE.md gotcha
  #3). Install with `--legacy-peer-deps`.

**Expected impact:** markers actually rendered per view become roughly constant,
independent of underlying flag count.

**Risk:** new dependencies, both platforms, and a visual/UX change (clusters look
different from pins). Worth doing before flag count meaningfully grows.

### Proposal E — photo thumbnails via Supabase Storage transforms
**Why it matters at scale:** photos are captured at `quality: 0.7` but stored and
served at full resolution, then displayed in a 72px Tasks thumb and a callout image.
Every Tasks row fetch downloads a full photo per row.

**Dashboard prerequisite:** Supabase Storage image transforms must be enabled on the
project (Settings → Storage → Image Transformation). I can't verify this unattended.

**Patch (after the toggle is confirmed on):**
```ts
// src/lib/flags.ts
export function flagThumbUrl(photoUrl: string | null, size: number): string | null {
  if (!photoUrl) return null;
  // photoUrl looks like:
  //   https://<proj>.supabase.co/storage/v1/object/public/flag-photos/<userId>/<file>
  // For transforms we need:
  //   https://<proj>.supabase.co/storage/v1/render/image/public/flag-photos/<userId>/<file>?width=…&height=…&resize=cover
  return photoUrl.replace(
    '/storage/v1/object/public/',
    '/storage/v1/render/image/public/',
  ) + `?width=${size}&height=${size}&resize=cover`;
}
```
Use `flagThumbUrl(flag.photo_url, 144)` for the Tasks card thumb (144 = 72px @2x
display density) and `flagThumbUrl(flag.photo_url, 480)` for the callout. Keep the
original full URL only where the user explicitly drills into the photo.

**Expected impact:** thumb payload typically 10–50× smaller than the original; major
bandwidth win as photo count grows.

**Risk:** if transforms aren't enabled, the transformed URLs will fail. Flip the
toggle first and verify with a single test render before rolling out.

### Proposal F — shared `flags` data cache (TanStack Query)
**Why it matters at scale:** `MapScreen` and `TasksScreen` each call `listFlags`
independently. Two screens fetching identical data twice. Refetch-on-focus then
multiplies that further.

- Add `@tanstack/react-query` (install with `--legacy-peer-deps`).
- One `useFlagsQuery(['open','verified'])` hook used by both screens.
- Invalidate the query on `updateFlagStatus` success.

**Expected impact:** round-trips per session ↓; navigating between Map and Tasks
shows cached data instantly while a single background refetch reconciles.

**Risk:** new dependency, ~150 LoC churn across both screens. Worth doing once the
app has a second or third screen reading flag data.

## Suggested next improvements (forward-looking)

1. **Move to bbox loading + the RLS initPlan rewrite as a pair.** They're the two
   highest-leverage things you can do *before* writing the next feature; doing them
   while the table is empty is essentially free, and locks in the right growth curve
   for everything you build on top. Proposals A and C together are probably 1–2 hours
   of work and protect the app to 100k+ flags.
2. **Wire `onRegionChange` into `PlatformMap` now, even before bbox loading lands.**
   It's the missing primitive: once it exists, swapping `listFlags` for
   `listFlagsInBbox` or `flags_in_view` is a small follow-up, and you'll also have
   the hook you need for marker clustering, "search this area" UX, and any future
   "tiles of pins" rendering. Adding it as a no-op now turns the bigger changes into
   small ones.
