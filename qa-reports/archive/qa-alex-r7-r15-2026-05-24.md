# Alex — WCAG 2.2 AA review of R7-R15 — 2026-05-24

Read-only review. No code touched. Branches reviewed against `main` (`f88ff7f`).

## Summary

Reviewed 9 feature branches across two cycles for WCAG 2.2 AA. Found **14 issues**: 4 HIGH (block users with disabilities), 6 MEDIUM (degrade experience), 4 LOW (polish). The dominant cross-branch pattern is **placeholder text using `color.textSubtle` (#999) which fails contrast** — present in R10, R13, and the pre-existing R14 search input. **One branch (R13) is unsafe to ship as-is** for low-vision users because the placeholder is the only visible label for the search input. R7 sort chips have a sub-44pt touch target that fails WCAG 2.5.5 (HIGH). All other branches are mergeable with cleanup tickets.

## Findings by branch

### R7 — Tasks sort chips (`feat/tasks-sort-2026-05-23`)

- [HIGH] **Sort chip touch target below WCAG 2.5.5** — `src/screens/TasksScreen.tsx:812` — `sortChip` style sets `minHeight: 36` with `paddingVertical: 8`. Effective hit area ≈ 36pt, below the 44pt minimum required by WCAG 2.5.5 (Apple HIG / Material guidelines both align). Sighted users with motor impairments will mis-tap. · Fix: bump `minHeight: 44` and adjust `paddingVertical` if needed to maintain visual height, or wrap in a Pressable with `hitSlop={{ top: 4, bottom: 4 }}` to extend touch area without enlarging visible chip.
- [MEDIUM] **Active sort chip text contrast borderline** — `src/screens/TasksScreen.tsx:820` — `sortChipText` is `fontSize: 13, fontWeight: '700'` (small text by WCAG: large = ≥18pt OR ≥14pt+bold). On active chip background `#2f80ed`, white text computes 3.87:1, below the 4.5:1 required for normal text. · Fix: bump font size to 14 (now qualifies as large text + bold, needs only 3:1) OR darken the active background to `color.brandOnSoft` equivalent / `#1f5fb3` (4.5:1+).
- [LOW] **`accessibilityRole="tab"` used outside a TabView** — `src/screens/TasksScreen.tsx:391` — RN's `tab` role announces "tab" to VoiceOver which can confuse users expecting a tab bar navigates between screens. `tablist` parent role is non-standard for RN. · Fix: change role to `"button"` and rely on `accessibilityState={{ selected }}` (already set) — that's the canonical RN segmented-control pattern (see iOS Apple HIG: Segmented Controls use Button role + selected state).

### R8 — Map long-press → drop (`feat/map-longpress-drop-2026-05-23`)

- [LOW] **Alert dialog reads raw lat/lng to SR** — `src/screens/MapScreen.tsx:652` — `Drop a new accessibility report at 37.12345, -122.65432.` Verbatim 5-decimal coords are noisy for blind/low-vision users via TalkBack/VoiceOver. Since long-press is a sighted-only path (FAB + AddressSearch remain — verified) it's not a blocker. · Fix: round to 3 decimals (≈100m precision) in the alert message OR omit coords entirely ("Drop a new accessibility report at the location you long-pressed?").
- [LOW] **No web-keyboard equivalent for long-press drop** — `src/components/PlatformMap.web.tsx:90` — Web variant uses `contextmenu` (right-click / long-touch). Keyboard-only users on web have no equivalent. The FAB-based flow remains as the accessible alternative, so the long-press feature degrades gracefully. · Fix (optional): document the FAB as the keyboard-accessible alternative in the user-facing help copy.

### R9 — Profile nearest-flag jump (`feat/profile-nearest-flag-jump-2026-05-23`)

- [LOW] **Could announce on appearance for SR users** — `src/screens/ProfileScreen.tsx:673` — The "Nearest unresolved" card appears when location resolves. Currently SR users may not notice it loaded after the Profile screen rendered. · Fix: wrap the conditional Pressable in a `View` with `accessibilityLiveRegion="polite"` so VoiceOver announces "Jump to the nearest unresolved flag..." when it appears post-location-resolve.

No HIGH or MEDIUM issues. Labels, hints, decorative icon hiding, contrast (5.98 + 8.95) all pass cleanly. Excellent execution.

### R10 — Help/FAQ search (`feat/help-faq-search-2026-05-24`)

- [HIGH] **Placeholder text is only visible label and fails contrast** — `src/components/HelpModal.tsx:139, 145` — `placeholder="Search…"` with `placeholderTextColor={color.textSubtle}` (`#999`) on `color.surfaceSoft` (`#f7f8fa`) = 2.68:1, below the 4.5:1 AA minimum for body text. There is `accessibilityLabel="Search FAQ"` for SR users but no VISIBLE text label, so sighted low-vision users with no SR cannot see the field's purpose. · Fix: either (a) add a visible label above the input (e.g. small "Search" caption), (b) keep the input always-filled with `value && placeholder` swap to a darker hint, or (c) use `color.text` (#333 → 12.5:1) for placeholder. Option (a) is simplest and most accessible.
- [MEDIUM] **FAQ card chevron now misses `importantForAccessibility`** — `src/components/HelpModal.tsx:215` — Pre-existing code has `accessibilityElementsHidden` on the chevron Text but not `importantForAccessibility="no-hide-descendants"` (the new search-clear ✕ added both, but the existing chevron still only has the former). Inconsistency — and on Android, `accessibilityElementsHidden` is a no-op (it's iOS only); only `importantForAccessibility` hides on Android. So Android TalkBack will read "▾" as "down-pointing triangle" after the question label. · Fix: add `importantForAccessibility="no-hide-descendants"` to the chevron Text (line 215).
- [LOW] **Search clear button (✕) missing for keyboard users on web** — `src/components/HelpModal.tsx:155` — `hitSlop={8}` on Pressable doesn't help keyboard-tab focus order. On web, the clear button only appears when there's text, so a sighted keyboard user typing then needing to clear must mouse-click. · Fix (web only, optional): add `onKeyPress` Escape-to-clear handling on the TextInput.

### R12 — Changelog collapsible (`feat/changelog-collapsible-2026-05-24`)

The new collapsible removes that role and rolls it into the Pressable label. Screen-reader users navigating by heading rotor (VoiceOver iOS) lose that affordance. · Fix: add `accessibilityRole="header"` to the inner releaseTitle Text inside the Pressable — both roles can coexist (the Pressable announces as button, the inner Text contributes the header semantic).

- [LOW] **Singular/plural string built without ICU** — `src/components/ChangelogModal.tsx:130` — `${itemCount} item${itemCount === 1 ? '' : 's'}` doesn't scale to localization. Not a WCAG concern, flag for Casey/i18n future work.

### R13 — My Reports search (`feat/my-reports-search-2026-05-24`)

- [HIGH] **Placeholder text fails contrast AND is the only visible label** — `src/components/MyReportsModal.tsx:283, 288` — `placeholderTextColor="#999"` on `#f7f9fc` background = 2.7:1, fails 4.5:1 AA. No visible label above the input — placeholder "Search your reports…" is the sole sighted indicator of field purpose. Same issue as R10 but more severe because the search bar replaces (visually) what was a normal list view. SR users have `accessibilityLabel` so they're fine; low-vision sighted users are not. · Fix: add a visible "Search" caption above the input OR use a darker placeholder color (e.g. `#666` = 5.6:1).
- [HIGH] **Empty-search-result message lacks `accessibilityLiveRegion`** — `src/components/MyReportsModal.tsx:443-448` — When user types a query and zero results return, the empty card renders silently. SR users get no announcement of state change. R10 sets `accessibilityLiveRegion="polite"` on its empty message; R13 does not. · Fix: add `accessibilityLiveRegion="polite"` to the outer Text or wrapping View of the "No matches" empty state.
- [MEDIUM] **Hard-coded color literals bypass design tokens** — `src/components/MyReportsModal.tsx:629-657` — Uses `#f7f9fc`, `#222`, `#eef1f5`, `#dde3eb` directly instead of `color.surfaceMuted / color.text / color.surfaceNeutral`. Design system drift makes future contrast audits harder. · Fix: replace with theme tokens (`color.surfaceMuted`, `color.text`, `color.surfaceNeutral`).

### R14 — Address search recents (`feat/address-search-recents-2026-05-24`)

- [HIGH] **Clear-recents link text fails AA contrast at small size** — `src/components/AddressSearchModal.tsx:497-501` — `clearRecentText` is `fontSize: font.size.sm (13pt)` + `fontWeight: semibold (600)` in `color.brand` (#2f80ed) on white = 3.87:1. Per WCAG, "large text" requires ≥18pt OR ≥14pt+**bold (700)**. 13pt+600 doesn't qualify, so the 4.5:1 normal-text rule applies. **Fails AA.** Affects any user with low vision trying to clear their recent searches. · Fix: bump to `fontSize: font.size.base (14)` and `fontWeight: font.weight.bold (700)` to qualify as large text, OR use `color.brandOnSoft` (#1c4f99) which gives 8.5:1 on white.
- [LOW] **Recent row chevron is decorative but `importantForAccessibility` missing** — `src/components/AddressSearchModal.tsx:248-252` — chevron Text has `accessibilityElementsHidden` only; on Android, this is a no-op. TalkBack will read "right pointing angle bracket" after each recent entry's display name. · Fix: add `importantForAccessibility="no-hide-descendants"` to the chevron Text. Same fix applies to the 🕘 glyph (line 242).
- [LOW] **`recentRow` label is good but `numberOfLines={2}` may truncate critical detail** — `src/components/AddressSearchModal.tsx:236` — visible text truncated to 2 lines is OK because `accessibilityLabel` carries the full displayName. Sighted SR users using both senses see truncated but hear full — possible disconnect for very long addresses. Acceptable trade-off. No fix needed.

### R15 — Feedback category filter (`feat/feedback-category-filter-2026-05-24`)

- [MEDIUM] **Chip count not in accessibilityLabel** — `src/components/MyFeedbackModal.tsx:147` — Active chip visually shows "Bug (3)" but `accessibilityLabel={`Filter to ${label}`}` — SR users don't hear the count. The user has no way to know how many feedback items match the active filter. · Fix: include the count when active: `accessibilityLabel={isActive ? `Filter to ${label}, ${filteredRows.length} ${filteredRows.length === 1 ? 'result' : 'results'}` : `Filter to ${label}`}`.
- [MEDIUM] **Filter change has no live announcement** — `src/components/MyFeedbackModal.tsx:139` — Tapping a chip silently re-renders the list with new data. SR users get no spoken confirmation that the filter took effect. Empty state message "No bug feedback / Tap All above…" appears with no liveRegion. · Fix: wrap the list's empty-state View in `<View accessibilityLiveRegion="polite">` OR have the chip itself announce on selection.
- [LOW] **Radio role without explicit radiogroup parent** — `src/components/MyFeedbackModal.tsx:144` — Chips use `accessibilityRole="radio"`. RN doesn't support `accessibilityRole="radiogroup"` natively, so the ScrollView has `accessibilityLabel` instead — acceptable workaround. The "radio" role announces correctly on iOS/Android. No fix required but worth noting if migrating to web.

## Cross-branch patterns

1. **Placeholder text color `color.textSubtle` (#999) fails AA contrast across all search inputs** — R10 (HelpModal), R13 (MyReportsModal), and the pre-existing R14 (AddressSearchModal) all use `#999` placeholders, computing 2.7-2.85:1 vs. white/surfaceSoft. The design-system token `color.textSubtle` documents itself as "for non-essential text or 18pt+" — but it's being used as the only visible label for primary input fields. **System-level fix needed:** introduce a `color.placeholderText = #666` (5.7:1) token and migrate all search inputs.
2. **Brand-color text on white at small sizes fails AA** — R7 active chip (white-on-brand 3.87:1, text 13pt+bold), R14 clearRecentText (brand-on-white 3.87:1, 13pt+semibold). The theme file documents `brand: #2f80ed → UI/large-text only`, but actual usage drifts into small-text territory. **System-level fix:** add a stricter convention: brand color requires `font.size.base + font.weight.bold` minimum, OR introduce `color.brandText = color.brandOnSoft (#1c4f99)` for text use cases.
3. **Decorative glyph hiding inconsistency** — R10 chevron, R14 chevron + 🕘 glyph use `accessibilityElementsHidden` without `importantForAccessibility="no-hide-descendants"`. On Android, only `importantForAccessibility` hides the element. TalkBack users hear "right-pointing angle bracket" etc. The newer code (R10 search-clear ✕, R14 clear-recents) gets it right with both attributes — older code is inconsistent.
4. **Empty/error states need liveRegion announcements** — R10 sets `accessibilityLiveRegion="polite"` on its empty FAQ-search result. R13, R15 do not. After a state-changing user action (typing, chip-tap), SR users need spoken feedback. **Pattern:** any text rendered conditionally as a result of search/filter input should be in a liveRegion.
