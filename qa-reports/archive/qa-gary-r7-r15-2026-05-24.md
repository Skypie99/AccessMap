# Gary — Test-coverage gap analysis for R7-R15 — 2026-05-24

## Summary

Reviewed 9 unmerged feature branches off main `f88ff7f`. Across 7 new lib files (R7, R9, R10, R11, R13, R14, R15) and 2 branches with no new lib (R8, R12), I count **18 gaps total: 3 HIGH, 8 MEDIUM, 7 LOW**. Overall coverage is strong — every lib has a well-structured Jest suite with input-mutation tests, NFC normalization where relevant, and AsyncStorage fail-soft coverage. The weakest coverage is **R12 (`feat/changelog-collapsible-2026-05-24`)**, where the pure helper `initialExpanded()` is inlined in the component and has zero tests. R7 (`tasksSort`) also has a small structural gap — it tests the *severity* tiebreaker thoroughly but doesn't pin the tiebreaker behavior for `newest`/`oldest` modes when timestamps tie. R8 has no extractable helper worth splitting out. The remaining libs are in good shape.

## Branch-by-branch gaps

### R7 — `tasksSort` (`feat/tasks-sort-2026-05-23`)

- **Current:** 14 tests covering: 3-mode order constant; labels for every mode; default; newest/oldest/severity sort; severity tiebreaker (newer first); input-not-mutated; stability when both keys tie; empty input returns a new array; load default/valid/garbage/unknown/throw/malformed-JSON; save persist + fail-soft.
- **Missing: [MED] `newest` mode tiebreaker on identical timestamps preserves input order** — the lib uses `a.i - b.i` as the secondary key for `newest`/`oldest` too, but only the *severity* mode's tiebreaker is asserted. A regression to a non-stable sort would slip through.
- **Missing: [MED] `oldest` mode tiebreaker on identical timestamps preserves input order** — same as above for the `oldest` branch.
- **Missing: [LOW] Behavior when `created_at` is unparseable** — `Date.parse('not-a-date')` returns `NaN`. The current comparator returns `NaN - NaN = NaN`, which means neither `<` nor `>` is true, and the sort silently falls back to the secondary key — which is actually the correct behavior, but it's not pinned by a test. Would catch a regression if someone switched to `+new Date(...)` and lost the NaN-safe tie path.
- **Missing: [LOW] `loadTasksSort` when stored value is a number/boolean** — `isValidSort` filters those out via strict `===` checks, but only the `{ weird: 'shape' }` and unknown-string branches are exercised. A literal `42` or `true` should also fall back to the default.

### R12 — changelog collapsible (`feat/changelog-collapsible-2026-05-24`)

- **Current:** No new lib file. The pure helper `initialExpanded(releases)` is defined inline at the top of `ChangelogModal.tsx` (lines 51-60 of the diff) and has **zero test coverage**.
- **Should-be-extracted: [HIGH] Extract `initialExpanded` to `src/lib/changelogExpanded.ts` and add tests** — it's pure, takes `ReleaseNote[]`, returns `Record<string, boolean>`, and the contract (first release open, rest collapsed, key shape `${date}-${i}`) is exactly the kind of thing that breaks silently if someone reorders the array or changes the key format. The expand-state map drives both rendering AND the accessibility state (`accessibilityState={{ expanded: isOpen }}`), so a broken initial map = a screen reader announcing every section as collapsed when one should be open.
  - Tests to add: empty array → `{}`; single release → `{ '<date>-0': true }`; multi-release → first is `true`, rest are `false`; two releases on the same date → both keys present (no collision due to index suffix); key format pinned to `${date}-${i}` so a refactor to a different key shape would break.

### R14 — `addressRecents` (`feat/address-search-recents-2026-05-24`)

- **Current:** 18 tests covering: addRecent empty/prepend/preserve-order/dedupe/case-insensitive dedupe/new-coords-win/cap-trim/purity/same-entry-rep-pick; loadRecents empty/round-trip/invalid-JSON/non-array/malformed-entry/hard-cap; saveRecents persist/trim-defensively/swallow-error; clearRecents removes/no-op.
- **Missing: [MED] `addRecent` with `entry.displayName` that is empty string** — `''.toLowerCase()` is `''`, which would match any other entry that has empty displayName. Edge case: caller passes a bad entry. Today `parseRecents` filters these out on load, but `addRecent` is a separate (in-memory) path. Test: `addRecent([SEATTLE], { displayName: '', lat: 1, lng: 1 })` → should the entry be added or rejected? The lib currently adds it. Pin the behavior either way.
- **Missing: [MED] `loadRecents` with `Infinity` / `-Infinity` lat or lng** — `Number.isFinite(Infinity)` is `false`, so `parseRecents` should drop it. The test fixture has `NaN coords` but not `Infinity coords`. A 1-line addition to the existing "drops malformed entries on load" test would close this.
- **Missing: [LOW] `parseRecents` with valid `id: ''` (empty string)** — the parser drops empty `id` but keeps the entry without an `id` field. Behavior is correct; pin it with a test fixture so a future refactor doesn't accidentally start including empty-string ids (which would break stable React keys).
- **Missing: [LOW] `addRecent` with `ADDRESS_RECENTS_MAX === 0`** — currently `5`. If the constant were ever bumped to 0, the function would always return `[]` (`.slice(0, 0)`). Not realistic, but pinning the constant-driven behavior with `expect(ADDRESS_RECENTS_MAX).toBeGreaterThan(0)` would catch an accidental zero in a refactor.

### R15 — `feedbackFilter` (`feat/feedback-category-filter-2026-05-24`)

- **Current:** 11 tests covering: 5-filter render order; every filter has a label; 'all' returns full list; each category filter returns only those rows (4 categories); empty input for every filter; no-match → []; input not mutated; generic type works; type-level reachability.
- **Missing: [HIGH] Confirm `'all'` returns the *same reference* (not a copy)** — the lib's source comment says "same reference is NOT guaranteed" but the implementation returns `items` directly. The component layer relies on referential equality for FlatList prop stability. A future "be defensive" refactor to `[...items]` would silently churn FlatList renders. A 1-line `expect(filterFeedback(rows, 'all')).toBe(rows)` would pin this. Without it, a real perf regression slips through unnoticed.
- **Missing: [MED] Input not mutated for the **non-'all'** path** — current `does not mutate the input array` test uses the `bug` filter (non-'all' path) ✅ — actually covered. Strike this.
- **Missing: [LOW] Drift test: every value in `FeedbackCategoryRow` is present in `FEEDBACK_CATEGORY_FILTERS`** — the type-level reachability test catches *filters → row types*, but not the reverse. If a new category (`'wishlist'`) were added to the DB enum, the filter list would be silently incomplete. A test that imports `FEEDBACK_CATEGORIES` from `src/lib/feedback.ts` and asserts every entry is in `FEEDBACK_CATEGORY_FILTERS` would pin parity.
