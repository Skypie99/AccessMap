# Design Pass — AccessMap — 2026-05-23

## Summary

First pass establishing AccessMap's design system. Inventoried every visual
literal in the codebase, built a token module (`src/theme.ts`) and a style
guide (`DESIGN.md`) as the single source of truth, applied tokens to two
isolated component slices (status pills + FlashBanner), and wrote design
specs for two upcoming features. **Typecheck green before and after.** All
work on branch `design/auto-2026-05-23`, not merged.

## Design system state

**Before:** no central token system. Visual values lived as inline literals
inside `StyleSheet.create` blocks across 11 screen/component files. The same
visual concept appeared with different hexes (sometimes the same hex in
different files duplicated by hand).

The inventory turned up:
- **47 distinct color literals**, dominated by `#fff` (×47 uses), `#eef1f5`
  (×23 — pill bg), `#2f80ed` (×22 — brand blue), `#666` (×21 — muted text),
  `#333` (×20 — body text), `#222` (×18 — headings).
- **13 font sizes** in use; 14pt and 13pt account for ~half of all text.
- **10 distinct `borderRadius` values**; 8 / 12 / 999 dominate.
- **30+ spacing integers**, clearly on a 4-pt grid.
- **Three rough shadow tiers** repeated by hand across components.
- **Duplicated visual constants** — the `STATUS_COLORS` palette is byte-for-byte identical in
  `MyReportsModal.tsx` and `FlagDetailModal.tsx`.

**After:** `src/theme.ts` exports six grouped namespaces (`color`, `spacing`,
`radius`, `font`, `shadow`, `a11y`, `severity`). `DESIGN.md` documents each
token, the WCAG-verified pairings, the component patterns (status pill,
filter chip, FAB, resolve/delete button, banner), and the decision log.

Centralized so far:
- All status pill bg/fg pairings.
- FlashBanner colors, shadow, type.

Still scattered (intentional — propose-only or larger slices for later):
- MapScreen styles (652-line file; staged migration in a future pass).
- TasksScreen, ProfileScreen, ReportFlagModal, the two PlatformMap wrappers.
- The `severityColor()` helper in `ReportFlagModal.tsx` still defines the
  same hexes a second time alongside `theme.severity` — should be migrated
  to source from theme in a follow-up.

## Specs & mockups produced

- **`designs/marker-clustering.md`** — visual + interaction spec for the
  Later-queue Map clustering feature. Cluster geometry, two-size scheme,
  color rationale (brand blue, never severity color), 44pt hit target rule,
  numeral overflow rule, spider behavior for co-located pins, per-zoom
  cluster distances, a11y cues. Key decision: clusters carry **count only**,
  not severity color — severity comes back when the cluster breaks apart.

- **`designs/profile-editing.md`** — visual + a11y spec for the Edit
  Profile sheet (already in flight on `feat/profile-edit-2026-05-23`). Edit
  affordance in the header, section-header typography, text input pattern,
  single-choice pill row, switch row + helper copy, Save / Cancel hierarchy,
  inline error banner reusing the MapScreen recipe from `LEARNINGS.md`. Key
  decision: default "prefer list view" ON if `isScreenReaderEnabled()` on
  first launch — design and accessibility are partners.

## Proposals (NOT applied)

### P1 — Migrate `severityColor()` to source from `theme.severity`

**Why.** The severity ramp is defined twice today — once as
`severityColor(s)` in `ReportFlagModal.tsx`, once as `theme.severity[s]` in
`src/theme.ts`. They agree by hand. The next time someone tweaks "Severe"
red, they'll only change one and the surfaces will drift.

**Described change.** Replace the body of `severityColor` with a lookup
into `theme.severity` and re-export both from theme. No visual change today
because the hex values are identical.

**Risk.** Low. One file edit + verify the existing callers (`MapScreen`,
`TasksScreen`, `MyReportsModal`, `FlagDetailModal`, `LegendModal`) still
type-check. Worth doing on its own commit so the rename / motion is easy to
review.

### P2 — Dark-mode token layer

**Why.** Outdoor / phone-out-while-navigating is the dominant use case for
AccessMap. A dark theme isn't a vanity feature — at dusk or at night a stark
white screen blows out the user's night vision and washes out the map
contrast that the rest of the design relies on.

**Described change.** Add a `theme.dark` mirror with the same token names,
re-pair every fg/bg combination for AA on dark surfaces (rough target
palette: surface `#0f1419`, surfaceMuted `#171c22`, text `#f0f2f5`, muted
`#a6acb3`, brand stays `#2f80ed` and now hits 5.5:1 on a dark surface, etc.).
A `useColorScheme()` hook in `App.tsx` selects light/dark. Add an explicit
"Theme" toggle in the proposed Edit Profile sheet for users who want to lock
one mode regardless of system setting.

**Risk.** Larger diff — every component that currently reads from `color.*`
gets it from a context-bound `useColors()` or a swapped module. The token
*names* don't change, so the change is mostly mechanical. Worth a small
spike on one screen (Profile) first to validate the approach.

**Mockup outline (described).** Profile screen with `color.surface = #0f1419`,
`color.text = #f0f2f5`, points hero card with subtle gradient from
`#1a2230` → `#0f1419`, brand-blue points-pill unchanged (looks great on dark).
The severity ramp is the same hex values; verify they still meet 3:1 contrast
against the dark surface (sev 1 green and sev 4 orange will need a check).

### P3 — Replace category emoji with a custom icon set

**Why.** Categories currently render as system emoji (🛑, ⚠️, etc.). Emoji
look different per OS, can't be themed (so they'll feel out of place in dark
mode), and don't always carry obvious meaning at the small sizes we use them
at. A small, monoline custom set would match the rest of the visual language
and read better on the map.

**Described change.** Adopt a small open-source icon set (e.g. Lucide via
`lucide-react-native`, MIT-licensed, ~30 KB tree-shaken) and replace the six
category emoji with named icons (`Construction`, `Stairs`, `ParkingCar`,
`DoorOpen`, `Bus`, `MoreHorizontal`). Always paired with the category text —
icon never alone (a11y).

**Risk.** Adds one dependency (must be propose-only per skill rules). Needs
the `--legacy-peer-deps` install path. Worth a focused spike to confirm
licensing and that it renders correctly on Android, iOS, and web.

   this pass.

## Forward-looking design suggestions

1. **A "design tokens linter" via grep.** Once token coverage is broader,
   add a `npm run lint:tokens` script that greps for raw hex literals
   outside `src/theme.ts` and fails CI if any are introduced. Cheap to
   build, makes the design system self-defending. Could ship the first
   version as a 20-line bash script in `scripts/lint-tokens.sh`.

2. **A `<StatusPill>` and `<FilterChip>` shared component.** Both patterns
   now exist in 2+ places with copy-pasted styles. Promoting them into
   `src/components/` (sourcing from theme tokens) would let future surfaces
   adopt them by reference and make a future dark-mode swap trivial. Defer
   until at least one more place needs them (don't abstract for two).
