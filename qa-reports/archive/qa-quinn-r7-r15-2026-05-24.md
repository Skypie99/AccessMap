# Quinn — Correctness review of R7-R15 — 2026-05-24

## Summary

Reviewed all 9 unmerged feature branches (R7-R15) for correctness, race conditions, state mismanagement, edge cases, and data-integrity. **17 findings total**: 2 HIGH, 4 MEDIUM, 11 LOW. Two branches need a fix before merge: **R8** (long-press drop is a no-op on web because `Alert.alert` is a no-op in `react-native-web`) and **R11** (silently regresses share on web — the main branch had a Web Share API / clipboard fallback, R11 strips it and `Share.share` rejects with "Share is not supported in this browser" on most desktop browsers). The other 7 branches are recommend-merge with optional small polish.

The pure-function libraries (`tasksSort`, `nearestFlag`, `helpSearch`, `shareFlag`, `myReportsFilter`, `addressRecents`, `feedbackFilter`) are all clean, well-tested, NFC-normalize where appropriate, and use the documented stable-sort / pure / fail-soft patterns. Most of the risk lives in the modal/screen wiring around them, not in the libs themselves.

## Findings by branch

### R7 — feat/tasks-sort-2026-05-23

- [LOW] **Hydration race vs. fast first-tap** — `src/screens/TasksScreen.tsx:82-91` — On mount, `sortMode` initializes to `DEFAULT_TASKS_SORT` ('newest') and `loadTasksSort()` runs in an effect. If the user taps a sort chip before the async load resolves (sub-50ms but possible), their tap is clobbered when the saved value (e.g. 'oldest') arrives and calls `setSortMode(saved)`. The `cancelled` flag only protects against unmount, not against a later user choice. · suggested fix: track `hydrated` boolean, set true after first user change OR after first load resolve; the load handler should noop if `hydrated === true`.
- [LOW] **Save fires before state commit, not after** — `src/screens/TasksScreen.tsx:91-95` — `handleSortChange` calls `setSortMode(next)` then `void saveTasksSort(next)` with the same value. Works because `next` is passed directly, not read from state. Worth a comment in case someone "fixes" it to read `sortMode` later. · suggested fix: add a one-line comment noting "we pass `next` directly so we don't read pre-commit state".

### R8 — feat/map-longpress-drop-2026-05-23

- [HIGH] **`Alert.alert` is a no-op on RN Web → long-press drop completely broken on web** — `src/screens/MapScreen.tsx:651-664` — `react-native-web/src/exports/Alert/index.js` defines `Alert.alert() {}` (empty body). On web, when the user right-clicks the Leaflet map (the `contextmenu` handler fires correctly), `handleMapLongPress` invokes `Alert.alert(...)` which does nothing — no confirm prompt appears, `setDropLocation` / `setReportOpen` never fire, the report modal never opens. The web variant of this feature is dead on arrival. · suggested fix: web branch should use `window.confirm()` (or skip the confirm entirely on web since right-click is intentional, not accidental like a touch long-press); native branch keeps the `Alert.alert` confirm.
- [LOW] **No platform-divergent confirm UX rationale documented** — `src/screens/MapScreen.tsx:641-666` — Spec says long-press on native + contextmenu on web. The native confirm prevents accidental pan-and-hold misfires; on web a right-click is deliberate, so the confirm step is just friction. Even after fixing the Alert.alert bug, web probably shouldn't show a confirm. · suggested fix: skip the confirm on web; go straight to `setDropLocation` + `setReportOpen`.
- [LOW] **Tests don't cover platform divergence** — no `*.test.ts` added for the new long-press wiring. `MapScreen` is harder to unit-test (lots of context wiring) but the long-press handler itself is pure-ish and could be extracted. · suggested fix: extract `handleMapLongPress` factory or skip — this is a low-priority gap given the manual-test path.

### R9 — feat/profile-nearest-flag-jump-2026-05-23

- [MEDIUM] **Profile now triggers a foreground-location permission prompt on first open** — `src/screens/ProfileScreen.tsx:170` + `src/lib/location.ts:42-79` — `useUserLocation()` requests `Location.requestForegroundPermissionsAsync()` on mount, with no guard. If a user opened the app, signed in, and navigated to Profile *without ever visiting the Map tab*, they now get an unexpected location prompt on Profile. This is a **privacy-sensitive change** per CONSTITUTION Art. 9 ("never act on a privacy-sensitive change — location, disability data, auth — without surfacing to Sky first"). The previous Profile screen never asked for location. · suggested fix: only call `useUserLocation()` if the user has already granted permission (read from a cached `permissionStatus`); or gate the nearest-jump UI behind an explicit "Find nearest" button that requests on demand.
- [MEDIUM] **Nearest-jump silently goes dark when Map filter excludes open/verified** — `src/screens/ProfileScreen.tsx:171-174` — `useFlags()` returns flags filtered by the user's *current* Map status-filter set. If the user has narrowed their Map filter to e.g. "rejected only" (to do an audit), Profile sees only rejected flags, `findNearestUnresolved` returns `null`, and the jump button vanishes even though there ARE open flags out there. Cross-screen coupling is invisible to the user. · suggested fix: have Profile call `listFlags(['open','verified'])` directly (small extra fetch) OR pass the unfiltered Map-tab flag set; document the coupling explicitly if accepting it.
- [LOW] **Button accessibilityLabel reads English-localized distance** — `src/screens/ProfileScreen.tsx:692-697` — `formatDistance` returns e.g. "0.6 km" but a screen reader will read "0.6 km" verbatim ("zero point six K M"); fine for now, brittle if you localize later. · suggested fix: when you add i18n, also expand the SR label to "0.6 kilometres away".
- [LOW] **No bound on staleness of `userLocation`** — `useUserLocation` is one-shot; user may have moved 5 km since opening the app but Profile still says "nearest = 0.3 km away". A "Refresh location" affordance would help. · suggested fix: add a small refresh icon on the button, or auto-refresh location on Profile-tab focus.

### R11 — feat/flag-share-2026-05-24

- [HIGH] **Web share regression — removed Web Share API + clipboard fallback** — `src/components/FlagDetailModal.tsx:153-180` — Main branch had a platform check that called `navigator.share` when available, fell back to `navigator.clipboard.writeText` with an alert, then `Alert.alert(message)`. R11 strips all of that and calls `Share.share({ message })` directly. RN Web's `Share.share` calls `window.navigator.share` if defined, otherwise **rejects with `'Share is not supported in this browser'`** (`react-native-web/src/exports/Share/index.js:42-46`). That error doesn't match the `/cancel|dismiss/i` regex, so users on Firefox desktop / older Safari / any browser without Web Share will see a "Couldn't share flag: Share is not supported in this browser" alert. Pre-R11 they got the message copied to their clipboard. · suggested fix: restore the platform-aware fallback inside `handleShare` — keep `formatFlagShareText` as the message source (the refactor is otherwise clean), but route the result through `navigator.share` / `navigator.clipboard.writeText` on web.
- [LOW] **Dead-code catch comment on native** — `src/components/FlagDetailModal.tsx:168-173` — The `if (/cancel|dismiss/i.test(msg)) return;` line is described as catching user-cancel, but on native iOS/Android `Share.share` **resolves** with `{ action: 'dismissedAction' }` rather than throwing on cancel. The catch isn't wrong, just usually unreachable. Harmless. · suggested fix: optional — check the resolved `result.action` instead/additionally for symmetric handling.
- [LOW] **`SEVERITY_LABELS` import dropped cleanly** — verified no other consumers of `SEVERITY_LABELS` remain in this file; import removal is clean.

### R14 — feat/address-search-recents-2026-05-24

- [MEDIUM] **`handleClearRecents` has a state-vs-storage race** — `src/components/AddressSearchModal.tsx:155-158` — Sets state to `[]` synchronously, then `await clearRecents()`. If the user closes the modal between the setState and the await resolving (rare but possible), and reopens it fast enough, the hydrate effect's `loadRecents()` could race with the `removeItem`. AsyncStorage queues most operations FIFO in practice but isn't guaranteed. Result on race: modal briefly shows the resurrected list. Self-heals on next open. · suggested fix: await the `clearRecents()` BEFORE setting state to `[]`, or use a sequence number on hydration to ignore stale loads.
- [LOW] **Move-to-front on re-pick of a recent is intentional, but spec says it** — `src/components/AddressSearchModal.tsx:140-152` — `handlePickRecent` re-adds the entry to bump it to position 0. Good. Comment is clear.

Five 250-char entries = ~1.5 KB of AsyncStorage. Fine for now, but consider truncating to ~120 chars to be safe across many writes. · suggested fix: optional — clip `displayName` to e.g. 150 chars on save.
- [LOW] **`accessibilityLabel` for recent rows doesn't say "tap" or position** — `src/components/AddressSearchModal.tsx:240-247` — Reads "Recent search: <name>" — fine. The `accessibilityHint` says "Centers the map…" — good. Minor polish opportunity to add position ("1 of 5") for orientation. · suggested fix: optional.

4. **Functional `setState((prev)=>...)` used in every relevant place** — R12's expanded-map toggle, R13's search query setters, R14's recent-list updates. No stale-closure bugs found.
5. **No per-user storage isolation issues.** All AsyncStorage writes are device-wide and the values (sort pref, address recents, expanded-state) are appropriately non-personal. R8 and R9 don't introduce AsyncStorage at all (correct).

## Suggested polish-loop tickets

**Ticket 1 (HIGHEST PRIORITY) — R11 web share regression**
Restore the web fallback in `src/components/FlagDetailModal.tsx` `handleShare`. Keep `formatFlagShareText` as the message builder (the refactor is clean and the tests are good). Wrap the `Share.share` call in a `Platform.OS === 'web'` branch that prefers `navigator.share`, falls back to `navigator.clipboard.writeText(message)` + an "Link copied" alert, then falls back to `Alert.alert('Share', message)`. Keep the native path as `Share.share({ message })`. Re-add `Platform` import. The error message `'Share is not supported in this browser'` (from `react-native-web`) is what's actually surfacing to users today on Firefox desktop and older Safari.

**Ticket 2 (HIGH PRIORITY) — R8 web long-press path is broken**
In `src/screens/MapScreen.tsx`, branch `handleMapLongPress` on `Platform.OS === 'web'`. On web, skip the `Alert.alert` confirm entirely (right-click is deliberate, not an accidental gesture) and call `setDropLocation(coord); setReportOpen(true)` directly. On native, keep the `Alert.alert` confirm to prevent accidental pan-and-hold misfires. Add a brief comment noting why the platforms diverge here. Consider adding an `Alert.alert` polyfill at the project level if other features depend on it on web — but for now a targeted fix is enough.

**Ticket 3 (NEEDS SKY DECISION) — R9 Profile-screen location prompt**
`useUserLocation` in `src/screens/ProfileScreen.tsx` triggers `Location.requestForegroundPermissionsAsync()` on mount. This is the first time Profile asks for location and constitutes a privacy-sensitive change per CONSTITUTION Art. 9. Three options for Sky to choose: (a) accept the prompt as the price of the feature (and document it in the release notes), (b) only call the hook after the user has already granted permission on the Map tab (cached `permissionStatus`), or (c) gate the nearest-jump UI behind an explicit "Find nearest" button so the prompt happens only on intent. Also fix the cross-screen coupling where Profile's nearest-jump silently hides when the user's Map status filter excludes open/verified flags — Profile should fetch `['open','verified']` itself rather than reuse the Map's filtered list.
