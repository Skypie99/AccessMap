## Section 2 — Reason for Ordering (mandatory spine)

**Why build first, then QA, then polish:**

1. **BUILD before AUDIT.** The QA agents needed concrete branches to read
   against — diffing main vs branch is how Quinn/Alex/Gary form findings.
   Spawning audits before there's anything to audit wastes a cycle.
   (Const. Art. 8.4 — auditors operate on artifacts, not intent.)

2. **AUDIT in parallel, all read-only.** Quinn, Alex, and Gary write to
   *different* qa-report files (`qa-{quinn,alex,gary}-r7-r15-2026-05-24.md`),
   so simultaneous filesystem writes don't conflict. None of them modify
   code (Const. Art. 9.2 — auditors never write code on the same pass).

3. **POLISH only after AUDIT.** Polish loops fixed specific findings
   cited by file:line in the QA reports. Without those reports, polish
   would have been guesswork. The polish commits each cite the finding
   they fix (e.g. "Quinn HIGH: Alert.alert no-op on RN Web" in PL-R8).

4. **Disjoint file ownership across all parallel waves.** Each wave-1
   build agent owned a unique component file + new lib + new test file
   (HelpModal / FlagDetailModal / ChangelogModal / MyReportsModal /
   AddressSearchModal / MyFeedbackModal — six different components, six
   new libs, six new test files). Wave-3 polish agents stayed on the
   same branch as their corresponding feature, touching only files
   already in that branch's diff. **Result: zero file-conflict risk
   across all 13 parallel agents.**

5. **Branched off main, not chained.** Last cycle's R7-R9 were chained
   (each off the previous), which made independent merge harder. This
   cycle's R10-R15 are each off `main @ f88ff7f` directly, so Sky can
   merge in any order. (LEARNINGS.md 2026-05-23 — "chained-branches
   complicate cherry-picking.")

6. **R9 NOT auto-fixed despite Quinn HIGH finding.** Quinn flagged that
   R9 introduces a foreground-location permission prompt on the Profile
   tab. Constitution Art. 9.6 says: "Never act on a privacy-sensitive
   change (location, disability data, auth) without surfacing it to Sky
   first via Morgan." Auto-patching R9 to silently move the prompt
   behind a button would be a privacy-meaningful UX change made without
   Sky's consent. So R9 is held as DECISION_FOR_SKY.

7. **Worktrees inside `.claude/worktrees/`, not external.** The initial
   `isolation: "worktree"` dispatch failed (harness was launched outside
   a git repo) but left 6 unlocked-able worktrees behind, on the correct
   branches at `f88ff7f`. Reusing those worktrees instead of clobbering
   and recreating was cheaper and avoided potential conflicts with the
   harness's worktree manager. New worktrees for R7+R8 polish were
   added under the same `.claude/worktrees/` parent for consistency.

## Section 3 — Blocked Nodes (mandatory spine — DECISION_FOR_SKY)

Tuples: `(node, blocker, options, recommendation, reversibility)`.

### B1 — R9 Profile location prompt
- **Node:** `feat/profile-nearest-flag-jump-2026-05-23`
- **Blocker:** Quinn HIGH finding — the Nearest-Unresolved-Flag card on
  Profile triggers `useUserLocation()` on mount, which can prompt for
  foreground-location permission. Constitution Art. 9.6 — privacy-sensitive,
  cannot ship without your sign-off.
- **Options:**
  1. **Ship as-is** — accept the new permission prompt on Profile tab
     (acceptable trade-off; the card hides itself when permission is
     denied, so it degrades gracefully)
  2. **Cached-permission gate** — only show the card if location
     permission was *already* granted (no new prompt); else hide
     silently. Minimal UX hit; safest privacy.
  3. **Explicit-CTA gate** — hide the card by default; show a "Find
     nearest flag" button that triggers the permission flow on tap
     (most user-controlled; one extra tap).
- **Recommendation:** **Option 2** (cached-permission gate). Mirrors
  how the Map screen already handles location. One-line change in
  `ProfileScreen.tsx` — replace `useUserLocation()` with a
  `useUserLocation({ requireExistingPermission: true })` variant, or
  read permission status first and conditionally render. Reversible.
- **Reversibility:** Trivial. Any option can be swapped later in a
  one-line change.

### B2 — R10–R15 cross-cutting placeholder color (#999) fails AA
- **Node:** R10, R13, R14 (plus likely others)
- **Blocker:** Alex flagged that `color.textSubtle = #999` is used as
  `placeholderTextColor` across multiple search/recents inputs. On the
  `#f7f9fc` modal background, contrast is 2.7:1 (needs 4.5:1).
- **Options:**
  1. **Per-branch fixes** — already done for R13 in PL-R13 (changed
     to literal `#5b6470`). Other branches (R10, R14) still use the
     subtle token.
  2. **Theme-level fix** — add `color.placeholderText = #666` (or
     `#5b6470`) to `src/lib/theme.ts` and migrate all uses.
- **Recommendation:** **Option 2** (theme-level), in a separate
  cross-cutting polish branch. Cleaner than scattering literal hex
  across components, and the next person who adds a search input
  will get the right contrast automatically.
- **Reversibility:** Easy (theme is one file).

### B3 — R10–R15 cross-cutting brand-color (#2f80ed) on small text fails AA
- **Node:** R7 (white-on-brand chip), R14 (brand-on-white link),
  others where brand is used as text color at <14pt+bold or <18pt.
- **Blocker:** `#2f80ed` doesn't qualify as "large text" under WCAG so
  the 4.5:1 floor applies → fails on white background (3.87:1).
- **Options:**
  1. **Per-branch fixes** — already done for R14 in PL-R14 (bumped
     font-size to 14pt to qualify as large-text). R7's white-on-brand
     chip passes for that color combo because the chip text is
     14pt+semibold on a saturated background.
  2. **Theme-level fix** — add `color.brandText = #1c4f99` for text
     use; keep `color.brand` for backgrounds/UI strokes.
- **Recommendation:** **Option 2**, in the same cross-cutting polish
  branch as B2.
- **Reversibility:** Easy.
