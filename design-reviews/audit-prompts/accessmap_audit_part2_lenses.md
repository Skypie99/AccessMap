L1 — FIRST IMPRESSION / ONBOARDING. A new, possibly disabled user opens the app cold: icon + splash (assets/, app.json), the onboarding carousel, the sign-in wall + guest affordance, the location-permission ask (timing, copy, denial path — the first privacy moment of an app that maps disability), the first map view. Within seconds: do they grasp what it does, that it is FOR them, and how to find barriers near them — accessibly (the SR first-open story from the a11y trees; is onboarding skippable and announced)? Does the first-run sequence earn trust or front-load friction? Pair with the R2/R6 reads.
L2 — VISUAL LANGUAGE + GLASS COHESION. Judge against the taste anchor with GLASS.md as LAW: per-screen tier correctness (§8/§12 conformance vs code); token discipline (no off-token inks/floors; the banned trio textSubtle/textMuted/brand on glass — GLASS §7.4); the ≥500-weight-on-glass type law; editorial type hierarchy; data-display legibility (severity ramp, distance, counts, status pills); theme parity; iconography + spacing rhythm; stage usage (pools, grain); the one-material read across all ~16 screens. Where does any screen wear the system wrong, half, or not at all — and where does restraint break (clutter, occlusion)? Consumes the arbiter results below.
L3 — THE TWO CORE FLOWS. Walk FIND and CONTRIBUTE end-to-end per orientation §3, plus onboarding + auth: every step's promise, feedback, and recovery (offline, permission denied, empty area, submit failure, slow network); cross-screen handoffs (Tasks card → Map focus, callout → detail); points/status feedback honesty (the flash-banner strings are coupled to the DB trigger values — check they still tell the truth); dead ends and leaks — SPECIFICALLY for someone with limited mobility, dexterity, or vision (pair with R1/R4). Boundary honesty: submit was never pressed — judge post-submit states as designed states from code, tagged.
L4 — MOTION. Inventory every animation system (RN Animated/Reanimated, sheet presentations, skeleton pulse, press sheen, map camera moves, carousel), each with file, trigger, duration/curve, native-driver?, RM-gated?, glass-law compliant (the glass itself carries no motion), whisper-or-noise verdict — THE MOTION INVENTORY TABLE is mandatory. Reduced-motion parity vs the OS setting (RM captures + code); vestibular safety of map zoom/fly-to; JS-thread animations that will stutter on device → NEEDS-SKY-DEVICE flags.
L5 — DEVICE INTEGRITY (not "responsive"). The four sizes + tablet as first-class citizens × both themes; Dynamic-Type stress (proxy shots + code-read maxFontSizeMultiplier walls + the DT guards); safe areas (notch, home indicator, status bar); keyboard avoidance on forms (ReportFlagModal, SignIn); one-handed reach zones per size (are primary actions in the thumb arc?); a 44pt HARD-floor census over EVERY interactive element (hitSlop counted; table by screen, top offenders named). ANY overlap/clip/occlusion at any size is HIGHEST severity. Landscape/tablet posture per app.json truth.
L6 — ACCESSIBILITY AS THE PRODUCT (weight this lens highest; pair with R2/R3). Full SR traversal scripts of BOTH core flows from the a11y trees + source: labels/roles/states/hints, grouping, focus order, accessibilityViewIsModal on every sheet/modal, announcements for async results (locating, results loaded, submit enabled). ★ THE MAP'S NON-VISUAL STORY — the app's hardest, most important question: what IS a blind user's mental model of a visual map of barriers? Is there a list-first equivalent for every map-only affordance (is NearbyFlagsModal the map's accessible twin?); are pins/clusters/heatmap reachable and meaningful; does severity survive without color (the "number AND a word" law); does anything announce on pan/filter? Contrast over glass AND over live tiles/heatmap [arbiter-measured]; Dynamic Type end-to-end; motor access (targets, gesture alternatives — pinch/drag/long-press each need a button path; the C-lite long-press's documented store path counts); cognitive load (jargon, memory demands, severity comprehension); TalkBack/Android parity code-read (the engineered-material path). Every failure names its mission cost. An AA breach on a primary surface is CRITICAL by default here.
L7 — FELT PERFORMANCE. Field reliability — a wheelchair user mid-route can't wait: map pan/zoom smoothness signals (JS-thread work in gesture handlers, marker churn, `tracksViewChanges` discipline per GLASS §12.6); the blur budget at the worst simultaneous state (+ tab bar); list virtualization law (never defeated — GLASS §3); cold-start weight; the photo pipeline (callout/thumbnail sizes); skeleton/spinner honesty incl. regression-watching the `initialLocationAction` locating fix; offline/poor-signal behavior (is anything cached? queued? honestly messaged?); battery/thermal risks (constant location watch? heat rendering?). Chromium proxies + code-inference, device-only truths flagged.
