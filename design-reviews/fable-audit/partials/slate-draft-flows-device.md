## flows-device-1 · Make the Report pill actually start a report (location parity on the Home-pill path)

**Resolves:** L3-1 (CRITICAL) · touches L3-5 finish-line context.
**Effort:** S · **Tier:** 1 (Haiku-safe mechanical parity) · **Signature:** no (it is a bug fix, not a moment) — but it is the single highest-leverage fix in the cluster.
**FORKS-TO-SKY:** Fork #3 (guest contract) — but *only* the "should web expose sign-in / request location at onboarding" half. This proposal's core (make the pill kick a location read) is a pure correctness fix that stands on its own and does not wait on the fork.

**What / why.** Today a first-time web guest taps onboarding's "Allow Location" (a pure web no-op, `OnboardingCards.tsx:243-249`), lands on Home, taps the advertised "Report" pill, and gets a sheet reading "Waiting for location…" over a permanently-disabled "Report anonymously" button — a false-promise status line above a dead submit, forever (skeptic proved byte-identical open vs t+25s, past the 15s GPS timeout). The mechanism is a one-line asymmetry: the FAB path (`MapScreen.tsx:2072`, auth-gated at `:2059`) fires `void requestLocation()` *before* `setReportOpen(true)`, but the Home-pill `openReport` handler (`MapScreen.tsx:1094-1096`) only does `setReportOpen(true)` — it never kicks a location read, and the sheet has no location hook of its own (`location` is a pure prop, `:78`). The fix is to make the pill path do what the FAB already does: on `openReport`, `if (!dropLocation) void requestLocation()` then open the sheet. That single call turns "Waiting for location…" into a real in-flight request that resolves to the coordinate line and enables submit. Pair it with two cheap honesty upgrades so the wait is never a lie: (a) if the request *fails or is denied*, the sheet's location line must switch from "Waiting for location…" to an actionable line with an in-sheet "Use my location" retry (mirroring Home's "Use my location" affordance), so recovery lives where the user is stranded instead of requiring them to abandon the flow; (b) the disabled submit gains an `accessibilityHint`/visible reason ("Add a location to submit") so R2 (blind) and R6 (first-timer) aren't left guessing why the button is dead. This is the CONTRIBUTE half of the entire product becoming reachable for the exact anonymous cohort it was built for.

**PROTECT preserved:** PROTECT-3 (ReportFlagModal sheet architecture — do not move the footer or replace the severity buttons; this only adds a location kick + a retry affordance inside the existing body) · PROTECT-8 (`POINTS`/anonymity honesty set — the anon banner alert and Sign-in-outside-it stay exactly as they are) · PROTECT-6 (the `82e738b` locating fix / `getCurrentPositionWithTimeout` anti-spinner spine — reuse it, don't fork it; the retry routes through the same `requestLocation`).

**Verification.** No arbiter needed (no color change). Manual: fresh web context WITHOUT geolocation grant → Home → "Report" pill → the sheet resolves to a coordinate and submit enables; deny the browser prompt → the location line offers an in-sheet retry and the disabled submit states its reason. Regression-watch: the FAB path and the auth flow are unchanged.

## flows-device-2 · Honest arrival: kill the "N flags nearby" lie and surface the denied-location banner on the arrival path

**Resolves:** L3-2 (CRITICAL) · L3-13 (viewport under-report, MEDIUM facet) · the "nearby is doing unpaid work" copy observation.
**Effort:** M · **Tier:** 1–2 (copy + a banner-gating fix; no query change) · **Signature:** no.
**FORKS-TO-SKY:** Fork #1 (PROXIMITY ARCHITECTURE). This proposal deliberately takes the "stop claiming 'nearby' until the query can back it" branch of that fork — it is the UI-only half. Whether AccessMap adds `ST_DWithin`-style spatial queries + a region-change fetch is Sky's data-layer call; this proposal does NOT touch `flags.ts` fetch scope.

**What / why.** Arriving on the Map with location denied or undetermined shows a citywide San Francisco map (`DEFAULT_REGION` 37.7749,-122.4194), zero pins in frame, and a pill asserting "5 flags nearby" — with no banner, no explanation, no recovery. R1 named this the single worst state in the app: "the one that would strand me… a flat lie," and for a Canadian app with flags in Kelowna, defaulting to SF makes the wrongness maximally visible. Two mechanisms, two fixes, neither of which touches the query: **(a) Truthful copy.** The pill's `flags.length` is a global, geo-unbounded count (`flags.ts:652-671`, no `lat/lng` clause) — so the word "nearby" is false in *every* state and merely becomes an outright lie when denied. Change the label to say what is actually true: "N reports loaded" (or "N reports" ), and let the "Sorted by distance / Showing most recent first" honesty already live in the list carry the ordering claim. This one word is the highest-frequency trust hit in the audit (R1's #1). **(b) Reachable denied-banner.** The well-written banner ("Location access is off…") exists but is gated on `permissionDenied`, which is set at exactly one site (`:999`, inside `requestLocation`) — so it only ever appears if the user manually taps the icon-only "Recenter." The mount 'clear' path (`:1043-1061`) clears the spinner but never sets `permissionDenied`. Fix: on the mount path, when `initialLocationAction` returns `'clear'` for a denied/undetermined status, set the state that renders the banner so the arrival itself explains the empty map and points to recovery. Also re-word the banner: today it says "Turn it on in your device Settings **to report barriers near you**" — wrong on two counts (the blocked job is FINDING, not reporting; and on web it is the *browser's* site permission, not device Settings). Frame it around finding, and make it web-accurate. (L3-13's "one pin under a 5-count" is the same defect's picture-half; the copy fix resolves the count/picture mismatch without a fit-to-flags feature — that stays a Fork #1 consideration.)

**PROTECT preserved:** PROTECT-2 (the Nearby list's honest no-location notice at `:198-204` — this proposal *aligns the pill to it*, never regresses it) · PROTECT-6 (locating fix — the mount path change only adds a `setPermissionDenied` in the already-existing 'clear' branch; the spinner-clear behavior that closed the prior CRITICAL hang is untouched) · PROTECT-10 (Home's honesty law — this extends the same "never claim what you can't back" principle to the Map pill).

**Verification.** No arbiter (copy + state gating, no color). Manual: `states/map__*__permission-denied.png` reproduction → the banner now renders on arrival and the pill no longer says "nearby." Confirm the granted path still reads correctly. Native first-run *feel* stays NEEDS-SKY-DEVICE (the logic is platform-independent; the on-device deny→arrival is Sky's).

## flows-device-3 · The map pin becomes a doorway: date on the callout + "Open details" that actually opens FlagDetailModal

**Resolves:** L3-12 (HIGH, callout cul-de-sac) · L6-05 (HIGH, the accessible list's only verb dead-ends) · L8-2 facet (callout omits date; verifier trust) · the "callout speaks severity numbers only" copy observation.
**Effort:** M · **Tier:** 2 · **Signature:** **YES (signature candidate).** This is the memorable, ownable, access-first moment: the app already *owns* a beautiful, SR-complete trust surface (FlagDetailModal) and simply refuses to hand it to map users. Wiring it in is the difference between "this app finds barriers" and "this app helps me act on them."

**What / why.** The FIND decision step dead-ends twice over. On the map, the pin callout (`PlatformMap.web.tsx:377-409` / `PlatformMap.tsx:239-277`) shows category + "Severity N · status" + photo + description — but **no created-at date and no action**, while its SR label literally promises "Open for details" / "Tap to view details" and opens nothing (cross-platform, per skeptic). R1: "severity 4, verified, 'wheelchair users have to detour' — and then nothing… a dead end exactly where I need a next step." Freshness is material — a year-old "verified" blocked path may be long cleared — yet the callout hides the age the Nearby list already shows ("29d ago"). Separately, the Nearby list (the app's accessible twin, PROTECT-1) has exactly one verb, `onSelectFlag`, which closes the list and centers the map (`MapScreen.tsx:2164-2181`) — the best accessible surface in the app dead-ends its only action in the visual layer that SR users can't perceive. **The fix is one wiring change with two entry points.** `FlagDetailModal.tsx` already exists, is imported by ~20 modules, and is SR-complete: `useFocusOnOpen` (`:125`), `accessibilityViewIsModal` (`:729`), `severityA11y`/`statusA11y` labels (`:45`), a real "Reported on {date}" line (`:926`), the photo gallery, and the StatusHistoryModal trust ledger (`:53`). MapScreen simply does not import it. Wire it so: (1) the callout gains a real "Open details" affordance that opens FlagDetailModal for that flag, and the callout itself gains the `created_at`/`relativeTime` line so even the quick-glance path shows freshness; (2) when the screen reader is on, route `onSelectFlag` to open FlagDetailModal instead of centering the map — turning the accessible list's dead-end verb into a doorway to the one surface that carries verifier provenance and a manageable focus target. This single move resolves a HIGH cul-de-sac, a HIGH accessible-dead-end, and part of a HIGH trust gap, by *adopting* an asset the app already built and hides.

**FORKS-TO-SKY:** L8-2's deeper "define 'verified' and show a verifier COUNT" is a trust-model scope decision (Fork #5-adjacent). This proposal scopes only the *reachability* of the existing detail surface + the callout date; it does not invent a verifier-count UI.

**PROTECT preserved:** PROTECT-1 (the Nearby list card grammar — untouched; only its terminal *verb's destination* changes, and only under SR) · the map overlay `pointerEvents="box-none"` gesture law (the callout affordance lives inside the callout, not the overlay) · PROTECT-3 is unaffected. Do not regress the list content; this extends it.

**Verification.** No arbiter (no color). Manual: tap a pin → callout shows a date and an "Open details" control → FlagDetailModal opens with focus managed on its title. With SR on (web forces it true), selecting a Nearby row opens the detail sheet rather than silently centering the map. Native focus traversal stays NEEDS-SKY-DEVICE.

A web guest gets zero feedback; a sighted signed-in user gets nothing visible either (skeptic confirmed "confirms nothing" holds all four cells: web-anon silent, web-auth silent, native-anon haptic-only, native-auth SR-hears-only). ## flows-device-5 · Give the map an honest zoom: app-styled 44pt zoom buttons in the overlay's bottom (unblocking web + adding the iOS zoom-out)

**Resolves:** L5-01 (CRITICAL) · the "status pill occludes the zoom control" copy observation · L3-3 flow-framing facet.
**Effort:** M · **Tier:** 2 · **Signature:** **YES (signature candidate).** Zoom is how a wheelchair user reads block-level detail; giving the flagship map a real, reachable, one-thumb zoom is a defining device-integrity win and an ownable "this map was built, not embedded" moment.

**What / why.** This is the defining device-integrity defect of the audit: an interactive control occluded at *every* device size. On web, Leaflet's default zoom buttons (26–30 CSS px, already sub-44) render top-left and are covered by the "5 flags nearby" pill and the wrapped action bar — "+" ~85% buried at 375/390/430, still buried at 834 — and worse, the skeptic proved the taps die on the un-guarded `topRow` wrapper (NOT `box-none`), so *even the visible pixels are pointer-dead* except a ~6px fringe. On iOS there are no zoom buttons at all: zoom is pinch/double-tap only, and double-tap zooms *in* single-fingered — the real gap is single-pointer **zoom-OUT**, a WCAG 2.5.7 gesture-alternative failure for R4's exact population ("zoom has no accessible fallback… slivers smaller than a fingertip"). **The fix (per the L5-01 fix-shape):** on web, `zoomControl={false}` on the `MapContainer` and render app-styled **44pt** zoom +/− buttons inside the overlay's *bottom* zone (thumb-reachable, away from the top pill), wired to the map's imperative zoom; on iOS, add the same app-owned 44pt zoom buttons (react-native-maps has no built-in ones), giving a single-pointer zoom-out that pinch alone doesn't. Both live in the app's own chrome, obey the 44pt floor written into `a11y.minTargetSize` (theme.ts:490), and — critically — must be mounted so their hit region is not stolen by the same un-guarded wrapper (the buttons go in a `box-none`-respecting group, mirroring `overlay`/`overlayTopGroup` at `:1259/:1265`). This turns "the least native surface in the app" (R5) into one that a one-handed user can actually operate.

**PROTECT preserved:** GLASS.md gesture law — the map overlay's `pointerEvents="box-none"` is *untouched*; the new zoom group must itself be `box-none` at the container with only the buttons intercepting, so map pans still pass through (this is a fix that RESPECTS the law by fixing a place — `topRow` — that already violated it). `GlassSurface.tsx` DO-NOT-EDIT (the buttons thread the primitive, no fork). No blur-budget change (buttons are chrome, not blur panes). Do not touch the Leaflet attribution (legally required — L5-16/L8-5 handle that separately).

**Verification.** No arbiter (button chrome, not a contrast token). Manual (web): the zoom buttons are 44pt, bottom-anchored, fully clickable, and map pans still work (gesture law intact). DevTools: `zoomControl={false}` present, no orphaned `.leaflet-control-zoom`. iOS single-pointer zoom-out + the pinch/VoiceOver map story stay NEEDS-SKY-DEVICE (the buttons are code-verifiable; the *feel* is device-only).

## flows-device-7 · Fix the two worst touch targets on the map: the bare-text "Clear" and the invisible action-bar overflow

**Resolves:** L5-04 (HIGH, ~34×17pt "Clear") · L5-05 (HIGH, action-bar tools scroll out of reach with zero affordance).
**Effort:** S (Clear) + M (overflow affordance) · **Tier:** 1–2 · **Signature:** no (device-integrity hygiene, but load-bearing for R4/R3).

**What / why.** Two named offenders in the 44pt census, both on the core FIND surface, both hitting limited-dexterity and low-vision users hardest. **(a) The filter panel's "Clear all filters"** (`MapScreen.tsx:1544-1552`) is the only bare-text `Pressable` in the entire app — no style, no `minHeight`, no `hitSlop` → ~34×17pt, adjacent to the 48pt-effective collapse chevron. It is the *recovery* action for the "my filters hid everything" state (R1's most-praised flow), so a limited-dexterity user who filtered themselves into an empty map now needs the panel's smallest target to escape — and a miss *collapses the panel* instead, reading as "my filters vanished." The fix is mechanical and already patterned: give "Clear" the same `minHeight: 44` + `hitSlop` the sibling `filterTitleRow` (`:2515`) got, with the same WCAG breadcrumb comment. **(b) The 7-button action bar** is a `ScrollView horizontal showsHorizontalScrollIndicator={false}` (`:1299-1304`); when its viewport shrinks below content width (iPad Split View ~320pt, true 320pt devices, web zoom/text-size), the LAST buttons — Refresh and **Recenter** — silently vanish with no scroll indicator, no fade, no peeking half-button. Recenter is not a convenience: the Report-FAB's own a11y hint tells locationless users "Use the recenter button to turn on location, then report" (`:2085`) — so when the tray hides it, the documented path into CONTRIBUTE disappears (R3 lost it at 1.3×). The fix adds a visible overflow affordance: a fade/gradient edge or a persistent "more" indicator so the hidden tools are discoverable, and/or guarantee a half-button peek at the scroll edge. (This respects the map-first top-anchored layout; it does not relocate the bar.)

**PROTECT preserved:** PROTECT-6 (the Map empty-filters recovery card — "Clear"'s fix must not regress the redundant 44pt "Reset all" path in the empty state, which is the belt to this suspenders) · PROTECT (L5) the action bar's 44×44 Pattern-B pins (the buttons can overflow but never be vertically crushed — the affordance is added *around* the ScrollView, the button geometry is untouched) · the virtualization law is unrelated and untouched.

**Verification.** No arbiter. Manual: "Clear" measures ≥44pt (code + inspector); at DT 1.3×/2.0× and ~320pt the action bar shows a discoverability affordance and Recenter is reachable. Split View / true-320pt device behavior stays NEEDS-SKY-DEVICE (the affordance is code-verifiable; the pane widths are device-only).

## flows-device-8 · Contain the Home map peek: one clean button, no tap-theft, no app-exit

**Resolves:** L5-06 (HIGH, live map inside the "Open the full map" button steals taps/scroll and can exit the app) · L4-06 motion facet (deduped into L5-06).
**Effort:** S · **Tier:** 1 (a `pointerEvents` wrapper + peek-instance map config) · **Signature:** no (a tidy, high-confidence quick win).

**What / why.** Home's map peek is announced to assistive tech as ONE button, "Open the full map" (`HomeScreen.tsx:257-269`) — but its interior is a *live* map with three conflicting behaviors. The skeptic probe was decisive: a wheel/scroll gesture over the peek zoomed the *preview* out to show all of San Francisco instead of scrolling the page or opening the map; and on web the peek embeds Leaflet's zoom buttons *and* the attribution anchors — so "+/−" zoom in place and **"Leaflet / OpenStreetMap / CARTO" are live links that navigate the browser away from the app entirely.** For a tremor user, "exit the app" from a mis-tap inside a *button* is the most disorienting failure available (R4 already treated the peek's zoom squares as reach targets). On native, react-native-maps' own gesture recognizers plausibly consume the tap before the parent Pressable sees it — i.e. the peek's tap-to-open contract may be a dead button on device. **The fix (per the L5-06 fix-shape):** wrap the peek's `<PlatformMap>` in a `pointerEvents="none"` layer so the whole 168pt tile region is inert and only the parent Pressable receives the tap → one clean "Open the full map" target with no tap-theft and no app-exit; on the web peek instance, also `zoomControl={false}` and relocate/suppress the attribution so no live third-party anchors sit inside a button (the *full* map keeps its legally-required attribution — this is only the decorative peek). This is a few lines and removes an entire class of the most disorienting failure (leaving the app) from the landing surface.

**PROTECT preserved:** GLASS.md gesture law is *not* in play here (the peek is not the map overlay) but the same discipline applies — the peek becomes strictly non-interactive, which is the safe direction. `GlassSurface.tsx` untouched. The full Map's attribution and gesture behavior are untouched (this scopes only the Home peek instance). PROTECT-10 (Home's honesty law) is unaffected — the peek still shows the map, it just stops stealing gestures.

**Verification.** No arbiter. Manual (web): wheel/scroll over the peek scrolls the page (not the mini-map); tapping the peek opens the full map; no Leaflet zoom buttons or live attribution links inside it. Native tap-to-open + drag behavior stays NEEDS-SKY-DEVICE (the `pointerEvents` wrapper is code-verifiable; the react-native-maps tap-swallow resolution is device-only).
